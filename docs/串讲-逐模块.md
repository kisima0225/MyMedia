# MyMedia 逐模块串讲

## 怎么用这份文档

这份文档的读者是**项目所有者本人**，用途只有一个：对着它把这个项目讲一遍，并且**答得出
追问**。spec §13 的风险表里写着一条"项目所有者无法解释自己简历上的项目"，这份文档就是
对那条风险的直接对冲。

用法建议：

- **按顺序读一遍，然后合上文档复述。** 12 节按依赖顺序排（11 个后端模块 + 前端），
  前一节是后一节的地基；跳着读会漏掉"为什么是这个顺序"本身传达的信息。
- **"最可能被追问的三个问题"那一栏是重点。** 每个答案都带了可核实的落点——类名、
  文件行号、迁移编号、ADR 编号或实测数字。**讲的时候要把落点讲出来**："我们用了
  `FOR UPDATE SKIP LOCKED`"和"`JobRepository.claimBatch`（`:26-33`）那条原生 SQL 用了
  `FOR UPDATE SKIP LOCKED`，而抢占方法上必须是 `REQUIRES_NEW` 事务，因为行锁只在事务
  期间有效"，是完全不同的两种回答。
- **答不上来时，回去读落点指向的那个文件，不要背这份文档。** 这份文档的每一条都是从代码
  里取出来的，代码永远是权威。
- **文档里有两处明确标出"文档与代码不一致"的地方**（§5 的 `content_hash` 覆盖率、
  以及交付 walkthrough §2.1 的 alpine 基础镜像）。它们**不是错误清单，是加分项**——
  能指出自己项目里文档跑偏的地方，比背熟一份没人验证过的说明书强得多。
- 更深的取舍去读 [`docs/adr/`](adr/) 的 15 篇 ADR，每个阶段做了什么去读
  [`docs/walkthrough/`](walkthrough/) 的 8 份。这份文档是索引与串联，不是替代。

一条贯穿全篇的判断，值得先说：**这个项目里几乎每一个"我们没有引入 X"的决定，都配了一个
"那我们用什么替代、它的边界在哪"的答案。** 没有引入消息队列（ADR-003/014）、没有引入
Elasticsearch（ADR-006/014）、没有引入 Redis（ADR-014）、没有引入组件库与 axios、没有做
微服务（ADR-009）、没有用 WebFlux（ADR-015）——每一条都能说出替代方案落在哪个文件、以及
什么时候该改主意。**"我没用"不是答案，"我没用，因为 A，我用了 B，B 的上界是 C，到 D 的
时候要重新评估"才是。**

## 1. `shared`

**它解决什么问题**：放那些多个模块都要用、但**不属于任何一个模块**的纯算法与纯契约类。
没有它，`NaturalSortKey` 这类东西要么被复制两份（两份很快就会不一致），要么被塞进其中一个
领域模块，逼出一条本不该存在的模块依赖边。它的 `allowedDependencies` 是**空的**——`shared`
不依赖任何模块，这是它能被所有人依赖的前提。

**关键设计**

- **只放算法，不放模型。** 里面是 `NaturalSortKey`、`MaterializedPath`、`SampledHash`、
  `HmacSigner`、`FieldMergePolicy` 这类无状态纯函数，以及 `NotFoundException`、
  `ScrapeStatus`、`SearchQuery` 这类跨模块契约。**没有任何领域实体**——`video` 与 `image`
  共享算法但不共享模型，这是 ADR-012 的地基。
- **第二个消费者出现时才提取，不提前抽象。** `SampledHash`（G8）与 `HmacSigner`（ADR-008）
  都是先在一个模块里长出来、出现第二个使用者时才提到这里，且提取时算法一个字节不动。
- **`GlobalExceptionHandler` 也在这里**：把 `NotFoundException` 统一翻译成 404，
  这是"404 而非 403"这条全局规矩的落点。

**最可能被追问的三个问题**

| 问题 | 怎么答 |
|---|---|
| 为什么 `SampledHash` 是从 `scan` 提上来的，而不是一开始就放在这里？ | 计划 02 引入它时**只有一个消费者**——改名检测（`RelocationDetector`），所以它是 `com.mymedia.scan` 下的 package-private 类。计划 06 做分片上传的秒传判定时出现第二个消费者（`upload.InstantUploadResolver` 经 `scan.ScannedFileHashService`），才提升到 `com.mymedia.shared` 并改 public，**算法一个字节不动**（这是 G8）。类注释里"住在 `shared` 的理由"那一段就是这么写的。反过来问自己：如果一开始就放这里，它会是一个"猜测将来会有人复用"的公共类——而 `shared` 里塞满这种猜测的项目，最后没人敢改其中任何一个。同一个先例后来又用了一次：`HmacSigner` 是在 `library.ShareTicket` 之外出现了第二个 HMAC 消费者（`user.MediaTicketService`）时，才从 `ShareTicket` 里提出来的（ADR-008）。**"第二个消费者出现时才提取"是这个项目的成文惯例，不是两次巧合。** |
| `NaturalSortKey` 解决什么问题？ | 字典序会把 `第1卷, 第2卷, 第10卷` 排成 `1, 10, 2`——这是媒体库必踩的坑，视频域的集号与图片域的卷号都依赖它。算法是把每一段连续数字替换成 `位数的位数 : 位数 : 去前导零的数值`（`10` → `1:2:10`，`2` → `1:1:2`），因为 `1:1:` 的字典序小于 `1:2:`，位数少的数字自然排在前面；位数相同则退化成按数值逐位比较。两个实现细节值得讲：**全程纯字符串操作，不解析成 `long`**（20 位以上的数字会溢出，而文件名里什么都可能出现）；**去掉前导零**使 `001` 与 `1` 得到相同的键。键在**写入时预计算**存进 `sort_key` 列（`image_node.sort_key`，`V8__image_domain.sql`），查询时直接 `ORDER BY`，不在每次查询时重算。 |
| `HmacSigner` 为什么被两套票据共用？ | 项目里有两处"服务端不存任何东西、校验就是重算一遍再比"的票据：`library.ShareTicket`（分享链接解锁后的通行证）与 `user.MediaTicketService`（登录用户的短期媒体票据）。**算法完全相同，生命周期完全不同**，所以复用算法、不复用票据类型——与 `NaturalSortKey`/`MaterializedPath` 是同一条"复用算法，不复用模型"。一个具体收益：`user` 模块因此仍然只依赖 `shared`，落地媒体票据时**没有碰任何 `allowedDependencies`**（ADR-008）。而两者的默认密钥行为**刚好相反**，这是最能说明"共用不等于同质"的一处：媒体票据密钥留空无所谓（TTL 15 分钟 + 前端提前 30 秒续签，重启后最坏只是多取一次票据）；分享密钥留空则是 G14 记录的用户可感知缺陷（重启后带密码的分享链接要访客重新输密码，所以 README 部署清单里 `MYMEDIA_SHARE_SECRET` 是必配项）。**同一段代码，两种默认值，理由各自独立成立。** |

## 2. `user`

**它解决什么问题**：身份。谁在请求、他是不是管理员、以及浏览器的 `<video src>` 这种带不了
请求头的场景怎么证明身份。没有它，"每个用户各自的播放进度""这个库谁能看"这些多用户语义
全部无从谈起。依赖只有 `shared`。

**关键设计**

- **HTTP Basic + 无状态，禁用 CSRF**（ADR-002）。服务端不存会话。
- **密码走 `DelegatingPasswordEncoder`**，哈希带 `{bcrypt}` 前缀（`SecurityConfig.passwordEncoder`）。
- **媒体票据是一条旁路，不是第二套认证**（ADR-008）：`MediaTicketAuthenticationFilter`
  装在 `BasicAuthenticationFilter` **之前**，只在三条只读路径上认票据，认完换成标准
  `SecurityContext`，下游控制器一行不改。
- **`AdminBootstrap` 幂等**：首次启动建初始管理员，已存在则跳过。

**最可能被追问的三个问题**

| 问题 | 怎么答 |
|---|---|
| 为什么是 HTTP Basic 而不是 JWT / Session？ | 三条（ADR-002）。**一，不用 Cookie 会话，浏览器就不会自动携带凭证，因此不存在 CSRF 攻击面**——`csrf().disable()` 是有理由的，不是图省事；在无状态 API 上加 CSRF 令牌是纯粹的复杂度。**二，相比 JWT 少了签发/过期/刷新/吊销四套机制**，而 JWT 的核心优势是跨服务传递身份，单实例部署用不上。**三，Session Cookie 要 CSRF 防护 + 会话存储**，对 SPA + REST 是额外负担。代价也要一起说：每个请求做一次 bcrypt 校验，有 CPU 开销（真成瓶颈可以在 Basic 之上加一层短期令牌缓存）；必须 HTTPS 部署，否则凭证明文传输——项目交付形态是本机 compose，不涉及公网。有一个细节能证明这不是照抄教程：`SecurityConfig` 把默认的 `BasicAuthenticationEntryPoint` 换成了 `HttpStatusEntryPoint(UNAUTHORIZED)`——**默认那个会在 401 上带 `WWW-Authenticate: Basic` 头，浏览器一见到就弹出原生密码框，SPA 自己的登录页再也没机会出现。** |
| 密码怎么存的？ | `PasswordEncoderFactories.createDelegatingPasswordEncoder()`，实际算法是 bcrypt，哈希带 `{bcrypt}` 前缀。**前缀不是装饰**：`DelegatingPasswordEncoder` 按前缀选校验器，所以将来换算法时，库里已有的旧密码仍然可以被校验通过、可以按登录逐个平滑迁移，而不需要强制所有人重置密码。同一套编码也用在分享链接的密码上——`V15__share_link.sql` 的 `password_hash` 列注释写着"存的是 `{bcrypt}` 前缀的委派编码"。 |
| `AdminBootstrap` 为什么是幂等的，它跟 demo 引导脚本的分工是什么？ | `AdminBootstrap.createInitialAdmin` 是一个 `ApplicationRunner`，第一件事就是 `repository.existsByUsername(username)`，已存在直接 return——所以重启安全，不会每次启动都试图重建、也不会把用户改过的密码刷回默认值。用户名/密码从 `mymedia.admin.username`/`password` 读，默认 `admin/admin`，创建时打一条 `log.warn` 提醒改密码。**分工的关键在模块边界**：`AdminBootstrap` 只碰 `user` 一个模块（`UserRegistrationService` + `UserAccountRepository` + `UserRole`，全在包内），写成 Java 是最自然的形态。而演示数据的引导要同时用 `library`（建库）与 `scan`（触发扫描），**现有 11 个模块没有一个的 `allowedDependencies` 同时允许这两条边**——为一段演示逻辑去动模块图代价太大，所以它是 `scripts/bootstrap-demo.sh`，用 `curl` 打项目自己的公开 API，零生产代码、零模块边界风险。**同一个问题，两种答案，差别只在于跨了几个模块。** |

## 3. `library`

**它解决什么问题**：媒体库是什么（名字、域、根路径、刮削器配置）、谁能看（`library_access`）、
以及怎么把一个条目分享给没有账号的人（`share_link`）。它是整个域分区体系的锚点——所有领域表
的 `domain` 列都外键指回这里。依赖 `shared` 与 `user`。

**关键设计**

- **域分区在数据库层强制**（ADR-001）：`UNIQUE (id, domain)`（`V3__libraries.sql:17`）+
  各领域表的复合外键 + `CHECK (domain = 'VIDEO')`。
- **无权访问一律 404**，不泄露资源存在性。
- **`metadata_providers` 是 `TEXT[]`，不做 JPA 映射**（`V3__libraries.sql:7`），走
  `JdbcTemplate` 直读直写（`LibraryService.metadataProvidersOf` `:52-56` /
  `setMetadataProviders` `:68-76`）。
- **分享链接用两个可空外键 + `CHECK`**，不用多态外键（`V15__share_link.sql`）。

**最可能被追问的三个问题**

| 问题 | 怎么答 |
|---|---|
| 域分区为什么要在数据库层强制？应用层校验不行吗？ | 要保证的不变式是"**条目的 domain 必须等于它所属库的 domain**"——这是一条**跨表**约束，而 PostgreSQL 的 `CHECK` **无法跨表引用**，所以它没法用单表 CHECK 表达。做法是在 `libraries` 上建一个看似冗余的 `UNIQUE (id, domain)`（`V3__libraries.sql:17`），各领域表冗余一列 `domain`，再用 `FOREIGN KEY (library_id, domain) REFERENCES libraries (id, domain)` 配合 `CHECK (domain = 'VIDEO')` 把它钉死——复合外键是 PostgreSQL 中声明式强制跨表不变式的标准手法，代价只是一列冗余（ADR-001）。为什么不只靠应用层：**任何一处忘了校验、或任何一次直连数据库的手工订正，都能写进脏数据**；分区是整个架构的地基，地基不能靠自觉。为什么不用触发器：能实现，但比声明式约束难读、难调试、性能更差。一个连带后果值得记住：**迁移脚本必须先建唯一键再建外键，顺序不可颠倒。** |
| 无权访问为什么返回 404 而不是 403？ | 403 会**泄露资源存在性**——"这个 id 存在，但你没权限"本身就是信息，攻击者可以靠遍历 id 把库里有多少条目、id 怎么分布摸清楚。项目的成文约定是：无权访问一律抛 `NotFoundException`。落点看 `VideoStreamService`（`:50-52`）：`if (!accessService.canAccess(userId, scanned.getLibraryId())) throw notFound(fileId);`，而 `notFound`（`:116-118`）返回的就是 `new NotFoundException("找不到视频文件 id=" + fileId)`——**和"真的不存在"走同一条出口，连错误消息都一模一样**，这是它有效的前提（两条路径的响应有任何差别，信息就又漏出去了）。`LibraryController` 的 `GET /{id}/metadata-providers`（`:46`）也是这个形状。这条规矩在媒体票据这条后加的通道上**自动成立**：`MediaTicketAuthenticationFilter` 只是把票据换成标准的 `SecurityContext`，`canAccess` 与 404 约定原样生效，27 个既有控制器一行没改（ADR-008）。 |
| 分享链接要指向"视频条目或图片节点之一"，为什么不用 `(target_type, target_id)` 多态外键？ | 因为**多态外键在 PostgreSQL 里建不了引用完整性约束**——理由就写在 `V15__share_link.sql` 的头注释里：`target_id` 这一列没法同时外键到两张表，删掉一个条目就会留下一条指向虚空的分享链接，而数据库不会拦。实际做法是**两个可空外键 + `CHECK (num_nonnulls(video_item_id, image_node_id) = 1)`**（约束名 `ck_share_link_single_target`），两列各自带 `ON DELETE CASCADE`。代价是加第三个域要改表结构（多一列多改一条 CHECK）；收益是每一列都有实打实的引用完整性，脏数据不可能产生。这与 ADR-012"两个域不共享模型"是同一条判断在另一处的体现——项目一直在避免"用一个类型列 + 一堆可空列表达两种东西"这个方向。另外两个设计点顺带能讲：**撤销是打标记而不是删行**（`revoked_at`，用户要能在列表里看见"这条我撤了"）；令牌是 32 字节 `SecureRandom` 的 Base64URL 无填充形式（43 个字符），**令牌本身就是凭证**（bearer capability），所以 `/api/share/**` 整段 `permitAll`。 |

## 4. `jobs`

**它解决什么问题**：扫描、刮削、预览生成、雪碧图、上传合并都是耗时的后台任务，需要排队、
并发消费、失败重试、以及"worker 死了怎么办"。没有它，这些活要么阻塞 HTTP 请求，要么散落在
各模块自己起的线程里，出错了没人知道。依赖只有 `shared`。

**关键设计**

- **`job` 表 + `FOR UPDATE SKIP LOCKED`，不引消息队列**（ADR-003 / ADR-014）。
- **去重用部分唯一索引**：`uq_job_dedup_active`（`V4__jobs.sql:23`）只在 `PENDING`/`RUNNING`
  上唯一——"同一个库不该被同时排两次扫描，但上一次完成后必须能再排"。
- **租约 + 指数退避**：`lease_owner`/`lease_expires_at` 两列，`BASE_BACKOFF` 30 秒起翻倍。
- **任务在虚拟线程里执行**（`JobScheduler.java:37`，ADR-015）。

**最可能被追问的三个问题**

| 问题 | 怎么答 |
|---|---|
| 为什么不用 RabbitMQ / Kafka？ | 四条理由（ADR-003），外加一条"什么时候该改主意"（ADR-014）。**一，`SKIP LOCKED` 提供了安全并发消费所需的全部语义**：多个 worker 并发查询时各自跳过已被他人锁住的行，拿到互不相交的任务集，且互不阻塞——这正是消息队列的核心能力。**二，任务历史天然可查询**（哪些失败了、失败原因、重试了几次），消息队列做同样的事要额外配一套持久化与监控。**三，入队与业务变更在同一个事务里原子提交**，不存在"业务写成功但消息没发出去"的双写问题。**四，少一个中间件**——交付目标是 `docker compose up` 一键启动。代价也讲清楚：**依赖轮询而非推送**，任务从入队到执行有最长一个轮询周期（5 秒）的延迟，对分钟级的后台任务无影响；高频轮询有持续的数据库负载，靠 `idx_job_claim`（`V4__jobs.sql:28`，`WHERE status = 'PENDING'` 的部分索引）把单次查询成本压到极低。**触发条件（ADR-014 写死了）：不是任务量，是架构形态**——出现第二个实例、或需要跨进程扇出订阅时才重新评估；只要还是"一个进程池内的多个 worker 抢同一张表"，就没有理由换。 |
| `FOR UPDATE SKIP LOCKED` 具体怎么保证不重复抢占？ | SQL 在 `JobRepository.claimBatch`（`:26-33`）：`SELECT * FROM job WHERE status = 'PENDING' AND scheduled_at <= :now ORDER BY priority DESC, scheduled_at LIMIT :batchSize FOR UPDATE SKIP LOCKED`。**但光有这条 SQL 不够，关键在事务边界**：`JobClaimService.claim` 上标的是 `@Transactional(propagation = REQUIRES_NEW)`，方法注释写明了为什么——**`FOR UPDATE SKIP LOCKED` 持有的行锁只在事务期间有效**，必须在同一个事务内把状态改成 `RUNNING`，其他 worker 才看不到这些行；**如果把查询与状态更新拆到两个事务，中间那个窗口就会让同一个任务被重复抢占**。`REQUIRES_NEW` 则保证即使调用方已在事务中，抢占也独立提交，让租约尽快对其他 worker 可见。顺带能讲去重：`uq_job_dedup_active`（`V4__jobs.sql:23`）是一个**部分**唯一索引，只覆盖 `PENDING`/`RUNNING`——这正好表达"同一个压缩包在上一轮索引任务 `SUCCEEDED` 之后可以再排一次"这个语义，而**MySQL 8.0 没有部分唯一索引**，要靠额外列加触发器模拟（ADR-010）。 |
| worker 进程崩了怎么办？ | worker 崩溃时没人把任务标记为失败，它会永远停在 `RUNNING`——**租约到期是唯一能察觉它已死的信号**。`JobRepository.reclaimExpiredLeases`（`:41-45`）把 `status = 'RUNNING' AND lease_expires_at < :now` 的行退回 `PENDING`、清空 `lease_owner`，供他人重新抢占（支撑索引是 `V4__jobs.sql` 里 `WHERE status = 'RUNNING'` 的 `idx_job_lease`）。活着的 worker 靠 `renewLease` 续期，续期语句带 `AND lease_owner = :owner AND lease_expires_at > :now` 三个条件——**这是为了让旧 worker 不能覆盖新 owner 的租约**：一个卡住又活过来的 worker 如果能盲目续期，就会把已经被别人接手的任务抢回去。续期跑在 `JobScheduler.java:39` 的 `heartbeatExecutor` 上（虚拟线程工厂建的调度池，ADR-015）。失败重试是指数退避：`JobClaimService.recordFailure` 用 `BASE_BACKOFF` = 30 秒，乘数 `1L << Math.min(attempts - 1, 10)`，即 30s → 60s → 120s…上限约 8.5 小时；达到 `max_attempts`（默认 3）就终结为 `FAILED`。**`recordSuccess`/`recordFailure` 都先走 `loadOwnedRunning` 核对"你还是不是这个任务当前的持有者"**，不是就打一条 warn 忽略掉——这是同一条防御的第三次出现。 |

## 5. `scan`

**它解决什么问题**：把磁盘上的文件变成数据库里的记录，并且在文件被改名、移动、删除、
恢复时**保住语义层挂在上面的一切**（进度、收藏、标签、刮削结果）。它是物理层的唯一所有者。
依赖 `shared`、`library`、`jobs`——**不依赖任何领域模块**。

**关键设计**

- **SPI 倒置**：`scan.spi.LibraryContentBuilder`（三个回调）由 `video`/`image` 反向实现，
  `scan` 不认识它们。`scan.spi` 与 `scan.event` 都标了 `@NamedInterface`。
- **绝不删除数据**：文件消失只把 `scanned_file.status` 置 `MISSING`（`ScanReconciler:64`）。
- **改名检测靠采样哈希**：`RelocationDetector.detectAndApply` 按（大小, 哈希）配对
  "消失的"与"新增的"，命中就原地改 `relative_path`、**`scanned_file.id` 保持不变**。
- **物理层不含任何领域语义**：`scanned_file`（`V5__scanned_file.sql`）只有
  `relative_path`/`size_bytes`/`mtime`/`content_hash`/`status`（ADR-011）。

**最可能被追问的三个问题**

| 问题 | 怎么答 |
|---|---|
| 为什么扫描不依赖领域模块，要做 SPI 倒置？ | `scan` 定义 `scan.spi.LibraryContentBuilder`（三个回调：`onFileDiscovered` / `onFileChanged` / `onFileVanished`），`video` 与 `image` 各自实现并注册成 Spring bean，`scan` 完全不认识这两个模块，加第三个域（音频）不用改扫描代码一行。**为什么这里倒置是对的：物理扫描真的与领域无关**——遍历目录、算指纹、对账、改名检测，没有一处需要知道文件是电影还是漫画页；倒置之后 `scan` 里**一个 `if (domain == …)` 都没有**，收益是实的。**而这个项目在 `preview`/`metadata` 上做了相反的判断**（ADR-004）：刮削本身就是领域特定的（TMDB 只管影视、Bangumi 的番剧与漫画走不同 type、NFO 字段名两个域也不一样），倒置只能把这些判断从 `metadata` 挪进两个领域模块，**判断的数量一个不少**，还多一层间接和一份要维护的接口契约。**同一个项目里对"要不要倒置"做出两次相反的判断，各有各的理由——这比"我全都倒置了"更能说明判断力。** 强制点是 `scan/package-info.java` 上的 `allowedDependencies = {shared, library, jobs}`，由 `ModularityTests` 的 `ApplicationModules.verify()` 在测试期强制（ADR-009 里有 RED/GREEN 实证：把 `video` 的依赖收成 `{"shared"}` 后测试立刻报出 11 条越界依赖）。 |
| 文件消失了为什么只标 `MISSING` 不删？ | `ScanReconciler.reconcile` 对遍历后没被认领的记录调 `leftover.markMissing()`（`:64`）——**这一行本身不删**。理由是"文件消失"这个信号本身很不可靠：外接盘没挂上、网络存储抖动、用户临时移走一个目录，都会让整批文件"消失"，而删掉就把 `scanned_file.id` 上挂着的全部语义状态（播放进度、阅读进度、收藏、标签、刮削结果）连根拔掉，**且不可逆**。文件回来时 `ScanReconciler` 认出 `existing.getStatus() == MISSING` 并置 `reactivated = true`（`:44`/`:52`），沿 `onFileChanged` 通知领域模块。**真正的删除是显式的**，只在语义层确认孤儿之后才发生：`VideoScanFinalizer` 与 `ImageScanFinalizer` 在 `LibraryScanCompleted` 事件之后各自清理"没有任何物理文件关联"的语义条目——注意**被标 `MISSING` 的 `scanned_file` 不触发清理**，只有语义条目彻底没有物理文件了才回收（ADR-011）。这条"扫描绝不删除数据"是跨计划的成文约定，所有"回收"逻辑都建立在它之上。 |
| 改名检测为什么用采样哈希而不是全量？它会漏什么？ | 算法是 `shared.SampledHash`：`SHA-256(8 字节大端 sizeBytes ‖ 采样区)`，采样区 = `size ≤ 2MB ? 整个文件 : 首 1MB ‖ 尾 1MB`。**长度必须参与摘要**，否则前缀相同、长度不同的文件会碰撞。理由：全量哈希一个 20GB 视频在机械盘上要数分钟，扫描承受不起。**它会漏**：两个首尾相同、仅中段不同的大文件会得到相同指纹；**能抓住的是**"换成了另一个文件、丢了整块首尾、总长度不对"（ADR-007）。改名检测的场景是"同一个文件换了位置"，首尾加长度对这个场景足够。还有一个"早先为 A 做的决定在 B 上白捡好处"值得讲：**这个算法形状让浏览器可以用 `File.slice` 只读首尾各 1MB、`crypto.subtle.digest` 算一次，就拿到与服务端一致的指纹**——如果当初选的是全量 SHA-256，用户要传一个 20GB 文件就得先在本地读完 20GB 才能问"你有没有"，秒传的意义所剩无几。<br><br>**这里有一处文档与代码不一致，知道它反而加分。** ADR-007 的背景、`ScannedFileHashService` 与 `InstantUploadResolver` 的类注释都写着"`content_hash` 绝大多数是 NULL，计划 02 只在改名检测需要时才算"。**代码不是这样**：`LibraryScanner.scan`（`:93-97`）在对账之后**无条件**遍历本库所有文件，对每个 `ACTIVE` 的调 `relocationDetector.ensureHash(root, file)`，而 `ensureHash` 第一件事是"已有哈希就直接返回"——这段自计划 02 引入它的提交（`48e409d`）起就没变过。所以真实情况是：**每个文件被哈希一次（在发现它的那次扫描里付掉），扫过一遍的库里 ACTIVE 文件基本都有哈希**，不是"绝大多数为 NULL"，也不是"每次扫描全量重算"。这不影响正确性（秒传的第一步反而更容易命中），但如果被追问"你说大多数是 NULL，那第一步查得到吗"，正确答案是"实际查得到，那三处注释与代码对不上"。 |

## 6. `video`

**它解决什么问题**：把一堆视频文件解释成"一部电影""一部剧的第 1 季第 3 集"，并且能真的
播放（HTTP Range 流式传输）、能记住每个用户播到哪。依赖 `shared`、`user`、`library`、`scan`
（含 `scan::spi` 与 `scan::events`）——**不依赖 `image`，也不依赖 `jobs`**（视频域不排任何任务）。

**关键设计**

- **语义树**：`video_item` / `video_group`（季、篇章）/ `collection`（`V6__video_domain.sql`），
  结构从文件名解析（ADR-012）。
- **文件名解析分层且绝不抛异常**（`VideoFilenameParser`），最差回落到去扩展名的文件名。
- **Range 严格按 RFC 9110 §14.1**，多重 Range 返回**并集**（`video/range/RangeParser`）。
- **进度挂在 `video_file_id` 上，不挂路径**（`V7__video_progress.sql`），且用户态数据独立成表。

**最可能被追问的三个问题**

| 问题 | 怎么答 |
|---|---|
| 文件名解析到什么程度就该停？ | `VideoFilenameParser` 是分层的：先从文件名取 `SxxExx`（`SEASON_EPISODE`，认 `S01E05`/`s1e13`），季号取不到就从**目录名**补（`SEASON_IN_DIR`，认 `Season 3`/`第2季`/`S03`），再单独找集号（`EPISODE_ONLY`，认 `E07`/`第11话`/`[08]`），另外抽年份与画质，并剥掉方括号/圆括号里的字幕组压制组标签。**任何一层失败都不影响其他层，且解析器不因非法或不完整路径抛异常**——最差情况返回去掉扩展名的原文件名当标题。**停在这里的理由是 ADR-005**：刮削是可选增强不是必经步骤，**扫描完成的瞬间条目就必须可用**（标题来自文件名解析、封面来自抽帧，可播放）。所以解析只需要好到"给出一个不难看的标题、把一部剧分对季集"，剩下的交给刮削，刮削不来就安静用文件名——`NO_MATCH` 不是错误，界面上不出现红色感叹号。再往下猜（猜发行版本、猜字幕组含义）收益递减而错误率上升，而**错误的元数据比朴素的元数据更糟**：用户看到一个错的标题会以为系统坏了，看到一个原文件名只会觉得"还没刮削"。 |
| Range 请求的完整语义是什么？多重 Range 怎么处理？ | `video/range/RangeParser` 按 RFC 9110 §14.1 实现，类注释列了三条最容易写错的规则：**`bytes=-500` 是"最后 500 字节"，不是"从 0 到 500"**；**Range 两端都是闭区间**，长度是 `end - start + 1`（差一错误在这里最常见）；**语法错误或不认识的 unit 应当忽略 Range 头、返回完整内容**，而不是报错——只有语法正确但区间越界才返回 416。区间用 `BigInteger` 解析再收敛，避免超长数字溢出。**多重 Range 的定稿是返回并集**（最小起点到最大终点，`:53-78`），不实现 `multipart/byteranges`——理由写在类注释里：浏览器的 `<video>` 元素不发送多重 Range，为一个没有真实客户端的分支实现一整套 multipart 编码不划算。这是 spec §14 的待定项之一，在计划 03 拍板定稿。可以补一句可验证的判据：拖动播放器进度条时，响应必须是 **206 Partial Content** 而不是 200——如果是 200，说明 Range 头被忽略了，浏览器会退化成"下完整个文件才能跳"。 |
| 播放进度为什么挂在文件上而不是路径上？ | `video_progress` 的主键是 `(user_id, video_file_id)`（`V7__video_progress.sql`），`video_file` 再外键指向 `scanned_file`。**路径是会变的**——用户整理媒体库这件事本身就是在改路径。挂路径的话，一次改名等于进度清零，而且是静默清零（新路径没有记录，看起来就像"从没看过"）。挂 id 之后，`RelocationDetector` 认出"这仍是同一个物理文件"就**原地更新 `relative_path`，`scanned_file.id` 不变**，外键指向它的一切语义状态都还在，不需要任何补偿逻辑（ADR-011）。V7 顶上还写着另一层理由：**用户态数据独立成表，绝不塞进媒体表**——同一部片子，每个用户有各自的进度，互不干扰；如果把 `position_seconds` 当成 `video_file` 的一列，多用户从第一天就不成立。两个附带细节：`idx_video_progress_continue` 是 `WHERE completed = FALSE` 的部分索引，直接服务"继续观看"这一条查询；`VideoProgress.COMPLETION_RATIO = 0.95`——**播到 95% 即视为看完，因为片尾曲期间用户通常直接关掉**。 |

## 7. `image`

**它解决什么问题**：漫画与图集没有视频那种命名约定，所以这个域不做语义解析，而是把
**用户自己的目录结构**当成组织结果，用任意深度的树表示，并且要能直接从 CBZ 里读单页。
依赖 `shared`、`user`、`library`、`jobs`、`scan`——**不依赖 `video`**。

**关键设计**

- **自由树 + 物化路径**：`image_node.materialized_path`（`/1/17/93/`）与 `sort_path`
  （`/1:1:1画师a/…`）两条路径（`V8__image_domain.sql`），子树查询走前缀索引。
- **"书"与"文件夹"不是互斥类型，而是同一节点的两种能力**（`readable` / `browsable`），
  `reading_mode`（`AUTO`/`FORCE_BOOK`/`FORCE_FOLDER`）让用户覆盖自动判定。
- **CBZ 绝不解压到磁盘**（`ImageArchiveReader`），用 Commons Compress 逐条目判编码。
- **批量集合操作走 `JdbcTemplate`**：`ImageLibraryRecalculator`（窗口函数重编页码）与
  `ImageTreeRelocator`（一条前缀替换 UPDATE 搬整棵子树）。

**最可能被追问的三个问题**

| 问题 | 怎么答 |
|---|---|
| 为什么图片域是自由树而不是像视频域那样的语义树？ | 因为两个域在"什么是一个条目"这件事上真实结构完全不同（ADR-012）。**视频的命名约定（`S01E01`、季号、集号）是行业级的、广泛遵守的**，解析它有真实收益——用户不用手动整理，系统就能正确分季分集。**漫画与图集没有等价物**：一本书在磁盘上可能是一个 CBZ、一个装满散图的目录、或者一个包着若干章节子目录的目录，不存在一套能覆盖大多数场景的命名规则。**如果强行给图片域也套一层语义解析，`reading_mode` 这种本该是"少数场景的例外"的覆盖开关，会变成"大多数场景都要手动纠正"的常态**——那比不做解析体验更差。所以 `image_node` 用物化路径表示任意深度的层级，**目录结构本身就是用户的整理结果**，系统不去猜。`V8__image_domain.sql` 的头注释还点出了核心设计：**"书"与"文件夹"不是互斥的节点类型，而是同一节点的两种能力**——所以 API 上一个节点可以同时 `readable` 与 `browsable`。这条判断一路贯穿到前端：视频域用等高 16:9 网格，图片域用不裁切的多列瀑布流（见 §12）。 |
| CBZ 怎么做到"绝不解压到磁盘"？ | `ImageArchiveReader` 的类注释第一句就是**"绝不解压到磁盘"**：ZIP 的中央目录区记录了每个条目的偏移量，可以直接定位并解压**单个**条目——读第 37 页就只解第 37 页，不碰其余的。用 Apache Commons Compress 而不是 JDK 自带的 `java.util.zip.ZipFile`，理由是**条目名编码**：JDK 版本要求整个归档用同一种编码，遇到解不开的字节直接抛异常；Commons Compress **逐条目**检查 ZIP 通用位标记第 11 位——打了标记的按 UTF-8 解，没打的才用构造时传入的**回退**编码（默认 GBK，可配 `mymedia.image.archive-charset`）。中文归档里两种条目混在一起是常态。这条已经实测过：同一个归档分别用 UTF-8 与 GBK 打开，条目名字节完全相同（`usesUTF8ForNames = true`），**所以把回退编码设成 GBK 不会破坏 UTF-8 归档**。一个连带设计：页表是"上一次解包解出来的快照"，所以 `ImageContentBuilder.onFileChanged` **不能空实现**（视频域可以，因为视频的语义结构不依赖文件内容）——包被重打（size/mtime 变了）或外接盘挂回来（`reactivated`）时必须重排 `ARCHIVE_INDEX`；而它排得出第二个任务，靠的正是 `job.dedup_key` 的部分唯一索引只覆盖 `PENDING`/`RUNNING`（见 §4）。 |
| 目录改名时怎么用一条 UPDATE 把整棵子树搬走？ | `ImageTreeRelocator.rewriteSubtree`（`:277` 起）是一条前缀替换：`SET materialized_path = ? \|\| substring(materialized_path FROM ?)`，`sort_path` 同理，`depth` 直接在 SQL 里由新路径算出来（路径形如 `/1/17/93/`，深度就是斜杠数减一）。**不逐层递归**——spec §7.1 明确要求。方法注释里有一句关键解释：**SET 子句右侧读到的 `materialized_path` 是行的旧值**，因为 PostgreSQL 的 UPDATE 用行的原始值求值所有表达式，所以一条语句里既能读旧值又能写新值。判定"是不是整个目录搬走了"的规则也要能讲：把本轮的移动按（旧目录 → 新目录）分组，某组的文件数**等于**旧目录节点下的全部文件数才算整体搬迁（并从基候选逐层上溯），否则只是零散文件搬家、逐个重挂。**这条路径上出过两次真实缺陷，能讲出来比讲"我用了物化路径"有价值得多**：**P2**——只搬到组的最底层节点，顶层目录整体改名时旧祖先被误判成空壳回收掉；**P7**——目录被**上移**（新路径比旧路径更浅）时下标越界，异常从 `ImageScanFinalizer` 冒出去，导致扫描任务本身失败、队列永不排空。两个都已修（P7 是提交 `19d5a6c`）并补了回归测试（`movingANestedDirectoryUpToTheRootKeepsItsNode` 等）。**它们说明"物理层路径变、语义层原地跟随"这条设计在实现上不是免费的。** 还有一个诚实的边界：判定用的缓冲区是**进程内**的（`ConcurrentHashMap`），扫描中途崩溃会丢掉本轮判定，下次扫描退化成逐文件重挂——代价是一次目录级的用户数据丢失，换来的是不引入额外的状态表，单实例下这个取舍是划算的（类注释里写着）。 |

## 8. `preview`

**它解决什么问题**：界面上每一张封面、缩略图、以及进度条悬停时浮出来的那一帧，都不是媒体
文件里现成的东西——要调 ffmpeg 抽帧、要读漫画首页、要拼雪碧图。这个模块把"从原始媒体派生
出可展示资源"这件事集中起来。依赖里同时有 `video` 与 `image`——**它是刻意不做 SPI 倒置的
两个模块之一**（ADR-004）。

**关键设计**

- **一条链顺序执行**：探测 → 回填 → 抽帧封面 → 缩略图 → 排队雪碧图（`VideoPreviewGenerator`）。
- **雪碧图固定 100 帧 10×10**（`application.yml:62-63`），于是永远只有一张图 + 一个 VTT。
- **失败语义分两档**：探测失败抛异常（值得重试），抽帧失败记警告后返回（重试无用）。
- **外部进程的 stdout/stderr 必须并发读走**（`ProcessCommandRunner:63-71`，虚拟线程），
  否则管道缓冲区满了就死锁——这是正确性问题不是性能问题（ADR-015）。

**最可能被追问的三个问题**

| 问题 | 怎么答 |
|---|---|
| 雪碧图为什么固定 100 帧、10 × 10？ | `DerivedAssetKind.SPRITE_SHEET` 与 `SpriteJobHandler` 的注释都写着同一句话：帧数与网格是固定的（`application.yml:62-63` 的 `sprite-frames: 100` / `sprite-columns: 10`），**于是永远只有一张图、一个 VTT**。这一个决定省掉了多图分页、跨图边界（一个时间点落在两张图之间怎么办）、按时长决定图数（那前端就得先问"这个视频有几张雪碧图"）的全部复杂度。代价是长片的时间分辨率低——两小时的片子每帧覆盖 72 秒——但**进度条悬停预览要回答的是"这一段大概是什么"，不是精确定位**，够用。还有一条太短的视频不做（`sprite-min-duration-seconds: 10`）。配套有一条实现纪律值得讲：**图块尺寸从生成结果读，不靠计算**——`scale=160:-2` 的高度由 ffmpeg 按源视频宽高比取偶数得出，在 Java 里重算必然对不上，**多读一次生成好的图，换 VTT 坐标一定正确**。前端那一半是零额外网络请求的：`ScrubBar.vue` 拿这一张图用 `background-position` 换帧。 |
| 为什么探测必须先于抽帧？ | `VideoPreviewGenerator` 的类注释一句话说完：**封面取时长的 10% 处，不知道时长就选不出抽帧点**（取 10% 而不是 0 秒，是因为片头往往是黑屏或制作公司 logo）。所以整条链"探测 → 回填 → 抽帧封面 → 缩略图 → 排队雪碧图"放在同一个处理器里顺序执行，而不是拆成两个任务——spec 的 job type 清单里本来也没有单独的 `PROBE` 类型。**更值钱的是失败语义分两档**，这是任务系统里最容易写错的地方：**探测失败 → 抛异常**（连容器信息都读不出来，通常意味着文件当下不可读——盘掉了、正在写入——值得按退避重试）；**抽帧失败 → 记警告后返回**（文件可读却抽不出帧是内容问题，重试多少次都一样，让任务成功结束、条目暂时没有封面即可）。**区分"重试有用的失败"和"重试无用的失败"，比统一重试或统一放弃都难，也都对**——统一重试会让一个坏文件永远占着队列，统一放弃会让一次磁盘抖动永久损失一批封面。 |
| 派生资源为什么可以整个删掉重建？ | 因为它们是**纯函数的产物**：输入是原始媒体文件，输出确定，不含任何用户状态。`application.yml:56` 的注释就写着"派生资源根目录，独立于媒体库路径，**可整个删掉重建**"；README 部署清单里 `mymedia-derived` 这个卷标的是"可以不备"（必须备份的只有 `mymedia-pgdata`）。删掉之后，`PreviewBackfill` 会在下一次 `LibraryScanCompleted` 之后把没有封面的条目重新排一遍任务（批量上限 500 条）。这条性质决定了两件实际的事：**备份策略只需要护住数据库与媒体本身**；以及**派生资源出问题时的收敛动作是"删了重来"而不是"就地修"**——不需要写任何修复逻辑，不需要判断一张封面是不是"坏的"。相对的，用户态数据（进度、收藏、标签、`locked_fields`）没有这个性质，它们只能靠备份，这也是为什么两类数据从一开始就分在不同的卷、不同的表里。 |

## 9. `metadata`

**它解决什么问题**：把条目从"一个文件名"变成"一部有简介、有年份、有标签的作品"，同时
**不让刮削变成入库的必经步骤**。它还兼管标签（`tag` / `video_item_tag` / `image_node_tag`），
因为标签天然要同时看两个域。依赖里同时有 `video` 与 `image`，**刻意不做 SPI 倒置**。

**关键设计**

- **提供者链**：`LocalNfo` → 配置的外部刮削器（按 `libraries.metadata_providers` 顺序）
  → `Filename` 兜底（`MetadataResolver`）。
- **优先级由两套既有机制表达，没有第三套 tier 比较**：链顺序管"谁先谁后"，
  `locked_fields` 管"谁不能被覆盖"（`shared.FieldMergePolicy`）。
- **刮削是可选增强**（ADR-005）：空 `metadata_providers` 的库直接 `NOT_APPLICABLE`、连
  任务都不排；`NO_MATCH` 不是错误；低置信度进 `scrape_candidate` 等确认，**绝不猜**。
- **客户端侧限流**：`min-request-interval: PT1S`（`application.yml:68`）+ 标识性 UA（`:67`），
  实现在 `HttpProviderSupport.throttle`（`:110`）。

**最可能被追问的三个问题**

| 问题 | 怎么答 |
|---|---|
| `scan` 做了 SPI 倒置，为什么刮削链不做？ | 这是同一个项目里对"要不要倒置"做出的**两次相反判断**（ADR-004），也是这个项目最值得讲的一组对照。倒置买到的是"新增一个域不改上游代码"，**这个收益成不成立，取决于上游是否真的与领域无关**。物理扫描真的与领域无关（见 §5）；**而刮削本身就是领域特定的**：TMDB 只管影视，Bangumi 的番剧与漫画走不同的 `type` 参数，NFO 的字段名两个域也不一样。倒置只能把这些判断从 `metadata` 挪进两个领域模块——**判断的数量一个不少**，还多了一层间接和一份要维护的接口契约。具体形态看 `SubjectFactory`：两个域的差异一共二三十行，集中在一个类里一眼能看完；倒置成 SPI 就是把这段拆成两个类分别塞进 `video` 与 `image`。预览生成同理：抽帧靠 ffmpeg、漫画封面靠读首页，这两件事没有共同的抽象可言，硬造一个 `CoverSource` 接口只会得到两个互不相干的实现。**代价也要说**：模块图上多两条边（`preview`/`metadata` → `video`/`image`）；加第三个域时确实要改 `SubjectFactory` 与任务分派——**但这是预期内的**，因为那时确实要为音频写新的刮削逻辑，不存在"不改就能用"的可能。**方向仍然是单向的**：删掉 `preview` 与 `metadata`，视频与图片域照样能扫描、能播放、能阅读。 |
| `locked_fields` 与链的顺序各管什么？ | spec §7.2 的优先级是 `用户编辑 > 本地文件 > 刮削 > 文件名`，它由**两套既有机制**共同表达，**不存在第三套 tier 比较**——这一点在 ADR-005 与 `FieldMergePolicy` 的类注释里都被特意强调过。**链的顺序管"谁先谁后"**（`MetadataResolver`）：`LocalNfo` 永远排最前且**不必写进配置**；配置的外部刮削器按 `libraries.metadata_providers` 的数组顺序依次问；高分（≥ `auto-apply-threshold` = 0.8）**命中即停**，后面的不再问；`Filename` 永远排最后，而且**它的结果不算命中**——应用的同时置 `NO_MATCH`，界面安静回落。**`locked_fields` 管"谁不能被覆盖"**（`shared.FieldMergePolicy.apply`，只有两条规则：跳过锁定字段、跳过空值——"提供者没给出的字段不该把已有的好数据洗成空"）。**而用户编辑走的是另一条路（`applyUserEdit`），根本不经过 `FieldMergePolicy`**：用户就是权威，没有什么能拦住他改自己锁过的字段。再补一条链级容错：一个提供者抛 `ProviderUnavailableException` **不会中断整条链**，先记下来接着问后面的；只有"什么都没得到**且**确实发生过故障"时才判 `ERROR` 让任务重试——**否则一个正在限流的 TMDB 会连带毁掉本来能命中的 Bangumi**。 |
| 置信度用的二元组 Dice 和 `pg_trgm` 的三元组有什么区别？ | `TitleSimilarity.between` 是**字符二元组的 Dice 系数** `2 × \|A ∩ B\| / (\|A\| + \|B\|)`，交集按**多重集**算（否则 `"AAAA"` 与 `"AA"` 会算出 1.0，显然不对）。**为什么不用编辑距离**：编辑距离在中文上很不稳——"进击的巨人"与"巨人"的编辑距离是 3，看起来很远，实际是包含关系；二元组重叠直接反映共有的字组。**为什么二元组不是三元组**：多数中文词是两个字，二元组的信息密度更合适。而数据库端的搜索走的是 `pg_trgm` 的**字符三元组**（GIN 索引），且 `similarity()` **只用来排序，不用来过滤**（ADR-006 实测：`'进击的巨人' % '巨人'` 是 `false`，相似度只有 `0.125`，低于默认阈值 `0.3`）。**同一个思路的两种落点，各自由约束决定**：数据库里三元组已经由扩展提供且有索引支持，换不了；应用层里中文短标题用二元组明显更准，也没有索引约束。`TitleSimilarity` 的类注释自己就点了这组对照。配套的三档阈值也要能说：≥ `auto-apply-threshold`(0.8) 自动应用，≥ `review-threshold`(0.4) 进 `scrape_candidate` 等用户确认，低于此**直接丢弃**——**中等相似度绝不猜**（ADR-005 第 4 条），因为一个猜错的标题比没有标题更难被发现。 |

## 10. `upload`

**它解决什么问题**：从浏览器往媒体库里传大文件——要能断点续传、要能秒传、要能在传完之后
自动出现在库里。它独立成模块而不是并进 `library`，因为它有自己的状态机（会话/分片/合并）、
自己的临时存储布局、自己的任务类型。依赖 `shared`、`user`、`library`、`jobs`、`scan`
——**不依赖 `video` 与 `image`**。

**关键设计**

- **分片体就是原始二进制**（`application/octet-stream`），不走 multipart（`UploadController`）。
- **秒传分两步**：先按 `content_hash` 查，未命中取同库同尺寸且哈希为空的候选**现算**
  （上限 8 个，`InstantUploadResolver.MAX_CANDIDATES`）。
- **同名文件永不覆盖**：追加 `(2)`、`(3)`（`UploadAssembler.availableName` `:109`）。
- **文件名净化是安全边界不是顺手清理**（`SafeFileName`）。
- **合并完落进媒体库根目录 + 触发一次增量扫描**——这就是它依赖 `scan` 的原因，也是
  compose 里媒体卷不能挂 `:ro` 的原因。

**最可能被追问的三个问题**

| 问题 | 怎么答 |
|---|---|
| 为什么绕开 multipart 直接收二进制分片？ | `PUT /api/upload/sessions/{id}/chunks/{index}` 的**请求体就是分片本身**（`Content-Type: application/octet-stream`），后端从 `HttpServletRequest.getInputStream()` 直接流式落盘。理由写在方法注释里：**Boot 的 multipart 默认上限是 `max-file-size=1MB` / `max-request-size=10MB`**（实测；Boot 4 里属性名仍是 `spring.servlet.multipart.*`，没有改名），而且解析器会把内容先缓冲一遍——对一个几 MB 的分片是白白多一次拷贝。**更根本的是：元信息全在 URL 里**（会话 id + 分片序号），multipart 唯一能提供的东西（表单字段）这里根本用不上，它只剩下开销。前端那一半要对称地绕开 JSON 封装：`api/client.ts` 的 `request()` 对任何非 `undefined` 的 body 一律 `JSON.stringify`，**`JSON.stringify(someBlob)` 会把一个几 MB 的二进制切片悄悄序列化成字符串 `"{}"`，前端毫无察觉地发出错误数据**——所以专门加了一个 `putBinary()`，复刻认证头拼接与 401 处理，但完全绕开 `JSON.stringify`。还有一条同类纪律：**分片大小必须读服务端下发的 `chunkSize`，不能客户端自己猜**——猜错的话每一片的偏移量都和服务端的 `totalChunks`/校验逻辑对不上。 |
| 秒传的边界在哪？ | 三条，必须一起说（ADR-007）。**一、采样哈希会漏掉中段差异**：两个首尾相同、仅中段不同的大文件会被判成"已存在"——用户以为传上去了，实际库里还是旧的那份；同样地，合并后的校验也抓不住中段损坏。**能抓住的是**"传了另一个文件、丢了整块首尾、总长度不对"。逐字节完整性由另外三层承担：TCP 校验和、TLS 的 AEAD、以及每一片 `written != expected` 的当场核对；剩下的风险窗口是"传输层全部通过、但中段内容恰好不同且首尾与库内某文件完全一致"，在自托管媒体库里可以忽略。**要说的是这句，不是"做了完整性校验"——后者把边界含糊掉了。** **二、秒传只在同一个库内生效**：查询按 `library_id` 分区（也是既有部分索引 `idx_scanned_file_hash` 的形状），这是有意的——媒体库的根目录可能在不同磁盘上，"库 A 里有"不代表"库 B 里也能看到"。**三、同尺寸候选现算上限 8 个**（`MAX_CANDIDATES`），超过就落空、走正常上传。上限存在的理由：一个库里可能有几百个大小恰好相同的文件（同一台设备导出的视频尤其容易撞），不设限，一个"创建会话"的请求就可能读上几 GB；8 × 2MB ≈ 16MB 是一次 HTTP 请求可以承受的 I/O。**落空的代价只是慢，不是错——这是一个安全方向的失败。**（补一句诚实的：第二步这条兜底路径的前提是"库里大量文件没有哈希"，而实际扫描已经把哈希填满了，见 §5 末尾那处文档与代码的不一致——所以它在实践中很少被触发。） |
| 同名文件为什么永不覆盖？ | `UploadAssembler.availableName`（`:109`）在目标目录已有同名文件时追加 `(2)`、`(3)`……，注释写着理由：**"绝不覆盖：那是别人的文件，而扫描是靠路径认文件的——覆盖等于悄悄换掉一部片子的内容，而目录树纹丝不动。"** 后半句才是要害：覆盖之后 `ScanReconciler` 看到的是"同一个路径、size/mtime 变了"，走的是 `onFileChanged` 而不是"发现新文件"，**语义条目还是原来那个**——标题、封面、刮削结果、标签、以及别人的播放进度全部留在原地，指向一份完全不同的内容。**这是一种不会报错、也不会被任何测试抓到的数据损坏**，只有用户点开才发现"这部片子怎么变成另一部了"。相邻的一条同类纪律是 `SafeFileName`——类注释第一句就是"**这是安全边界，不是顺手清理**"：净化后的名字会被拼进媒体库根目录下的文件系统路径，一个没处理干净的 `../` 就是一次任意写。它处理的每一条都对应一个真实问题：两种目录分隔符（客户端可能是 Windows、服务端可能是 Linux）、纯点名 `.`/`..`、控制字符（日志注入与不可见文件名）、`<>:"\|?*`（Windows 上根本创建不了）、**结尾的点与空格（Windows 静默吃掉，导致写进去的名字与读出来的对不上，下一次扫描会把它当成另一个文件）**、以及超长截断。 |

## 11. `web`

**它解决什么问题**：两件事——全局搜索（唯一需要同时看见两个域的功能），以及把 Vite 构建
产物托管起来、让前端的 history 路由在刷新时不 404。`allowedDependencies` 是
`{shared, user, video, image}`，它是**唯一**可以同时依赖两个领域模块的地方。

**关键设计**

- **全局搜索分区返回、不混排**（ADR-013）：`GlobalSearchDto.Response(query, video, image)`，
  未命中的一边是**空数组而不是省略字段**。
- **两次查询顺序发出，不并行**——各自都是走索引的 SQL，为省几十毫秒引入线程池是用复杂度
  换不需要的性能。
- **SPA 兜底有两条"老实 404"的例外**：`api/` 开头的不存在路径、带扩展名的缺失文件
  （`SpaWebConfig.SpaFallbackResolver`）。
- **缓存策略不能一刀切**：`/assets/**`（带内容哈希）长缓存一年，`index.html` `no-cache`。

**最可能被追问的三个问题**

| 问题 | 怎么答 |
|---|---|
| 为什么只有全局搜索放在这个模块？ | `web/package-info.java` 自己写着答案：**全局搜索是本项目唯一需要同时看见两个域的东西**，因此也是唯一可以同时依赖 `video` 与 `image` 的地方。把它塞进任何一个领域模块，都会让其中一个依赖另一个——而 `video` 与 `image` 互不出现在彼此的 `allowedDependencies` 里（ADR-009 附表），这是域分区在模块层面的表达。收藏、分享、搜索这些功能之所以在两个域里**各有一套**（`VideoFavoriteService` / `ImageFavoriteService` 等），正是同一条约束的结果：宁可对称重复，也不引入一个"通用媒体条目"抽象把两个域粘起来（ADR-012 / ADR-013）。所以这个模块小得几乎只有两个类（`GlobalSearchController` + `SpaWebConfig`）——**小是结论，不是遗漏**。这里也是 spec §4.2 早就声明、但直到计划 06 才真正需要创建的模块：**没有真实需求之前不建模块**，与 `shared` 那条"第二个消费者出现时才提取"同源。 |
| 搜索结果为什么分区不混排？ | 响应形状是 `GlobalSearchDto.Response(query, video, image)`——`video` 与 `image` 是两个独立数组，**未命中的一边是空数组而不是省略字段**。两条测试专门钉住这件事：`returnsTwoPartitionedArraysRatherThanOneMixedList` 与 `aDomainWithNoHitsIsAnEmptyArrayNotAMissingField`（`GlobalSearchControllerTest:70` / `:81`，后者查"剧场版"只命中视频域时断言 `$.image` 是 `hasSize(0)` 而不是字段缺失）。**直接理由**：两个域的卡片布局、比例、可用操作都不一样，混排之后前端第一件事就是把它们再拆开——抽象没有省掉这个判断，只是把它挪到了更差的位置。**还有一个不那么明显、但更值钱的收益**（ADR-006）：分区返回意味着两个域各跑一次自己的查询，**不需要跨域的分数可比性**——搜索的排序是**分层**的（子串命中 → `similarity` → `ts_rank` → `sort_title`）而不是加权求和，正是因为 `similarity` 落在 0–1、`ts_rank` 通常是 0.0X 量级，**两个分数根本不在一个尺度上**，加权求和只是把"我不知道怎么比"包装成一个数字。分区之后，连"视频的 0.6 和图片的 0.6 谁大"这个问题都不需要回答。 |
| SPA 的 history fallback 与安全白名单会不会打架？ | 不会，因为**两层各管各的**。**`SpaWebConfig` 管"这个路径返回什么内容"**：`/video/items/12` 是一个**前端**路由，用户在这个地址刷新时浏览器会发一个真实的 GET，服务器上没有这个资源，不兜底就白屏。所以 `/**` 走 `SpaFallbackResolver` 兜回 `index.html`——但有两条**老实 404** 的例外：`api/` 开头的不存在路径（兜成 HTML 会让前端拿一坨 `<!doctype html>` 去 `JSON.parse`，**报出的错完全指错方向**），以及带扩展名的缺失文件（缺失的 `.js` 返回 HTML 会报 `Unexpected token '<'`，排查方向被彻底带偏）。缓存也不能一刀切：`/assets/**` 是 Vite 带内容哈希的产物，可以长缓存一年；`index.html` 不带哈希、是告诉浏览器该找哪些哈希文件名的入口，**一旦被长缓存，发一次新版后浏览器还攥着旧的 index.html 去请求早已不存在的文件，白屏且无法自愈**。**`SecurityConfig` 管"这个路径要不要登录"**：静态资源与前端路由整段 `permitAll`——**登录页本身就是静态资源，要求登录才能拿到登录页是个死循环**；真正的数据全在 `/api` 下，那里仍然 `anyRequest().authenticated()`。两个白名单是两套清单、服务两个不同的问题，不是重复。两个容易被追问的细节：`/api/share/**`（**单数**）整段 `permitAll`，而管理端点 `/api/shares`（**复数**）不被这个模式匹配、仍然要登录（`ShareAccessControllerTest` 钉住了这件事）；`favicon.svg` 与 `favicon.ico` **两个都要放行**，因为浏览器取图标的请求不带 `Authorization` 头，漏掉哪个，每个页面（包括匿名的登录页与分享页）都会多打一次注定 401 的请求。 |

## 12. 前端

**它解决什么问题**：把计划 01–06 做完的全部后端能力——扫描、播放、阅读、预览、刮削、
搜索、收藏、分享、上传——变成浏览器里能用的东西。独立的 Vite + Vue 3 + TypeScript 工程，
由 `frontend-maven-plugin` 绑进 `mvn` 生命周期，产物进 `target/classes/static/`，**随 jar
单容器交付**。全过程没有新增任何 Flyway 迁移，也没有给后端加任何新依赖。

**关键设计**

- **刻意不引入三样东西**：UI 组件库、CSS 框架、HTTP 客户端库。依赖只有
  `vue` / `vue-router` / `pinia`。
- **媒体票据只在三条只读路径上被接受**（ADR-008）。
- **一套 CSS 令牌两套取值**：`[data-domain='video']`（`tokens.css:50`）与
  `[data-domain='image']`（`:64`）。
- **组件渲染不写单元测试，只测不碰 DOM 的逻辑模块**：8 个测试文件、68 条 Vitest，覆盖
  `lib/` 下的六个纯函数模块（`reader` 翻页状态机 / `throttle` / `sampledHash` /
  `chunker` / `sprite` / `duration`）与 `api/` 里的 `media`、`ticket` 两条无 DOM 依赖的
  逻辑，**一个组件挂载测试都没有**。

**最可能被追问的三个问题**

| 问题 | 怎么答 |
|---|---|
| 为什么不引组件库 / CSS 框架 / axios？ | `frontend/package.json` 的 dependencies 只有三个：`vue` `vue-router` `pinia`。理由与后端"不引入无法解释的中间件"（ADR-014）是同一条：**一个媒体库的界面元素就是卡片、网格、进度条、面包屑**，套一个几百 KB 的组件库既讲不出理由，又会**把两套刻意做出差异的视觉语言压成组件库的默认样子**——而那两套差异恰恰是这个项目在表现层唯一的主张（见下一格）。原生 `fetch` 足够用，而票据与 401 处理本来就要自己写一层封装，axios 只是多一层要理解的抽象。**这条克制还有一个可验证的副产品**：`tools/screenshots/`（Playwright，要下几百 MB 浏览器）被刻意放在 `frontend/` 之外、也不接进 Maven 生命周期——**产文档资产的工具不该出现在应用的依赖树里**。另外所有依赖一律写精确版本、不写 `^`/`~`，这条有实测背书：npm 上 `typescript@latest` 现在是 Go 原生重写的 `7.0.2`，包内**不再导出 `./lib/tsc` 子路径**，而 `vue-tsc@3.3.11` 正是靠 `require.resolve('typescript/lib/tsc')` 启动，配 TS 7 直接 `ERR_PACKAGE_PATH_NOT_EXPORTED` 崩溃；而 `vue-tsc` 的 peer 依赖只声明 `typescript: ">=5.0.0"`——**这个声明是过宽的，拦不住你升级到一个它实际跑不起来的大版本**。实测过 5.9.3 通过、6.0.3 通过、7.0.2 崩溃。 |
| 媒体票据为什么只在三条只读路径上被接受？ | 先说清约束：`<video src>` / `<img src>` 由浏览器自己发起 GET，**没有任何办法附带自定义请求头**——这不是 HTTP Basic 的缺陷，**换成 Bearer JWT 一样带不了，换成任何"凭证放在请求头里"的方案都一样**。所以这三条只读媒体路径改用 query 参数携带一张短期 HMAC 票据（形状 `<userId>.<过期时刻>.<base64url 签名>`，TTL 15 分钟，前端提前 30 秒自动续签）。**代价是真实的**：凭证会漏进服务器访问日志、跨站请求的 `Referer`、浏览器历史记录。**路径白名单是对这个后果的直接缓解，不是回避**：`MediaTicketAuthenticationFilter` 只在 `/api/video/stream/**`、`/api/image/page/**`、`/api/assets/**` 三条上认票据（`:37-39`），**泄漏的代价上界因此被钉死在"有人多看了几部片子"，而不是"有人删了媒体库、改了用户资料"**。而且过滤器装在 `BasicAuthenticationFilter` **之前**、认完就换成标准 `SecurityContext`，下游 27 个既有控制器**一行没改**——`@AuthenticationPrincipal`、`canAccess`、"404 而非 403"全部照常生效，它们根本不知道这条通道存在。备选方案也要能答：**Cookie 会话**能让标签直接工作，但要推翻 ADR-002——重新引入 CSRF 攻击面与服务端会话状态，代价是架构性的；**fetch 成 blob URL** 图片勉强可行，视频不可行——一部电影要整个读进内存才能拿到 blob URL，而且完全丢掉 HTTP Range 与浏览器原生的拖动定位，把计划 03 里技术含量最高的那条链路直接作废。 |
| 两个域的视觉语言怎么用一套 CSS 令牌表达两种物理隐喻？ | 主题是一句话：**视频发光，图片反光。** 这不是修辞，它决定了每一个令牌的取值。`styles/tokens.css` 里 `[data-domain='video']`（`:50`）与 `[data-domain='image']`（`:64`）各定义一套**同名**令牌：底色一冷一暖（`#08090e`，"影院的黑不是中性的，屏幕溢光把它染蓝" / `#12100d`，"台灯下纸堆阴影的暖黑"）；强调色一琥珀一朱红（`#ffb020` 放映灯 / `#c0483a` 印泥，"不是霓虹的红"）；签名令牌 `--elevation` 一个是**彩色外发光**、一个是**黑色落影**。`AppShell.vue` 按路由 `meta.domain` 给 `<body>` 打 `data-domain`，一套令牌两套取值。**因为用的是属性选择器而不是根元素类，它可以套在任意元素上**——全局搜索页把两段结果各自包一层 `data-domain`（`SearchView.vue:104` / `:115`），**同一屏上两个域看起来就是两种东西**，这是整套体系最能说明问题的一屏。唯一的例外是阅读器：`--page: #f2ede3` 是**全应用唯一的亮面**，只在阅读器里满幅出现——暗框围着一页亮的漫画会产生光晕，长时间阅读很难受；而这个视觉突变也让"从浏览页进了阅读器"这件事被身体直接感知到，不需要读任何文字提示。**最后把它接回数据层**：视频域用等高 16:9 网格（`VideoCard.vue:66` 的 `aspect-ratio: 16 / 9`，视频封面天然接近这个比例，裁切基本无损），图片域用 CSS 多列瀑布流不裁切（`NodeGrid.vue:37` 的 `columns: 5 200px` + `break-inside: avoid`，窄屏降到 `:49` 的 `columns: 3 140px` 与 `:55` 的 `columns: 2 130px`，因为漫画封面比例天差地别，强行裁成统一比例会把标题文字或角色脸切掉）。**这不是"两处恰好都不一样"，而是"不一样"本身就是同一个根因——视频有统一形状、图片没有——在数据层和表现层的两次必然结果**（ADR-012）。 |
