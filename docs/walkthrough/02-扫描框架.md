# 扫描框架 Walkthrough

本文从一次媒体库扫描的完整链路解释当前扫描框架的设计取舍：`DirectoryWalker` 读取磁盘快照，`ScanReconciler` 把快照对账到 `scanned_file`，`RelocationDetector` 负责识别改名和移动，最后通过事件和 SPI 把物理文件交给具体媒体域。入口由 `ScanController` 接收 HTTP 请求，`ScanTrigger` 把请求放入持久化任务队列，`LibraryScanJobHandler` 再调用 `LibraryScanner.scan` 执行实际工作。

## 1. 为什么分开物理层与语义层

物理层只回答“磁盘上有什么文件、它现在在哪里、什么时候看到过”，因此 `src/main/java/com/mymedia/scan/ScannedFile.java` 的 `ScannedFile` 保存 `libraryId`、`relativePath`、大小、mtime、采样哈希和 `status`，并用数据库 `id` 作为稳定身份。语义层则应该回答“这个文件是一部什么作品、有哪些章节、用户看到哪里”，它通过 `src/main/java/com/mymedia/scan/spi/LibraryContentBuilder.java` 的 `LibraryContentBuilder` 接收 `ScannedFileDiscovered` 和 `ScannedFileVanished` 事件；当前阶段先把这个边界和事件契约建立起来，视频或图片模块可以在边界外维护自己的实体和进度。

改名时，`src/main/java/com/mymedia/scan/RelocationDetector.java` 的 `detectAndApply` 先按大小和采样哈希配对“新记录”和 `MISSING` 记录，再删除代表新路径的临时记录，调用 `ScannedFile.relocateTo` 更新原记录的 `relativePath`。这个方法保留原 `id`，并把状态恢复为 `ACTIVE`，所以语义层将来以 `scanned_file.id` 为外键保存的观看进度、收藏和手工元数据都不需要迁移；真正变化的只是物理位置（以及必要时重新保存的哈希）。如果物理记录和语义记录合成一张表，改名就容易被实现成“删除旧行、插入新行”，外键 id 会变化，进度和元数据要么丢失，要么需要额外做脆弱的级联迁移，这正是分层的主要价值。

## 2. 为什么快速指纹使用 size + mtime

`src/main/java/com/mymedia/scan/DirectoryWalker.java` 在访问普通文件时只读取 `BasicFileAttributes.size()` 和 `lastModifiedTime()`，放入 `ScannedEntry`；`src/main/java/com/mymedia/scan/ScanReconciler.java` 的 `isContentChanged` 只比较大小和经过 PostgreSQL 微秒精度归一化后的 mtime。这样每个文件的变化判断是常数级元数据读取，整次扫描的主要成本是遍历目录，而不是为每个视频从头读到尾。对一个几十 GB 的视频逐个计算全量哈希会把一次目录扫描变成大量磁盘 I/O，尤其不适合机械盘、网络盘和首次启动场景。

这不是内容一致性的数学证明：如果某个工具修改了文件内容后把大小和 mtime 都恢复成原值，`isContentChanged` 会把它判为未变化，旧的 `contentHash` 也不会被清除。当前设计把这种漏判风险换成日常扫描的可接受速度；需要高保证的导入或校验场景应显式执行全量哈希，而不能把 size + mtime 当成安全校验。mtime 的精度转换集中在 `ScannedFile.toPostgresPrecision`，避免文件系统纳秒值与数据库微秒值之间产生每次扫描都变化的假阳性。

## 3. 采样哈希的取舍

`src/main/java/com/mymedia/scan/SampledHash.java` 使用 SHA-256，并把文件长度先混入摘要；文件不超过两个 1 MiB 窗口时全量读取，否则只读取首 1 MiB 和尾 1 MiB。`RelocationDetector.ensureHash` 在文件仍然存在时补齐哈希，`detectAndApply` 先用大小分桶，再比较哈希，因此改名检测通常只需读取固定的 2 MiB，而不是读取完整媒体文件。

这种指纹仍然可能碰撞：两个长度相同的大文件只要首尾各 1 MiB 相同、中间内容不同，就会得到相同结果。这里接受该取舍是因为目标是识别“同一个媒体文件换了路径”，常规媒体文件的首尾和长度足以作为工程上的高性价比证据，且避免扫描 20 GB 文件的全量 I/O；它不是抗恶意构造的内容证明。若业务将来面对不可信输入或必须证明字节级相同，应增加全量 SHA-256 或在配对后进行二次全量校验。

## 4. 符号链接为什么可能成环

假设媒体根目录是 `media`，其中 `media/电影/回指` 是指向 `media` 的符号链接；跟随链接后，遍历会再次看到 `电影/回指/电影/回指`，理论上可以无限重复同一棵目录树。`src/main/java/com/mymedia/scan/DirectoryWalker.java` 明确使用 `FOLLOW_LINKS`，因此不能只依赖默认不跟随链接的行为。它先用 `root.toRealPath()` 得到规范化根路径，再在 `preVisitDirectory` 中对每个目录调用 `toRealPath()`，把解析后的真实路径放入全局 `visitedRealPaths`；同一个真实目录通过不同链接再次出现时，`add` 返回 false，立即 `SKIP_SUBTREE`。这会把“不同字符串路径”归并成同一个物理目录，从而剪断环；`maxDepth` 和 `visitFileFailed` 还提供了深度及单点访问失败的额外边界。

## 5. 为什么文件消失后不删除

`src/main/java/com/mymedia/scan/ScanReconciler.java` 会把本轮没有出现在遍历结果中的 ACTIVE 记录调用 `ScannedFile.markMissing`，仅把状态改为 `MISSING`；`src/main/java/com/mymedia/scan/ScannedFileStatus.java` 也明确规定绝不因暂时不可见而删除记录。外接硬盘未挂载、SMB/NFS 网络存储短暂不可达，都会让整棵目录在一次扫描中看起来消失；此时删除物理记录会连带让语义层无法找到原 id，用户的进度、收藏和手工元数据也会一起蒸发。

保留记录还使恢复路径简单：存储重新挂载后，同一路径会在 `ScanReconciler` 中命中既有记录，`ScannedFile.touch` 把状态恢复为 `ACTIVE` 并保留 id；如果文件确实换了路径，则由 `RelocationDetector` 走采样哈希配对。语义构建器的 `LibraryContentBuilder.onFileVanished` 也要求把语义条目标记为不可用而不是删除，查询缺失记录则由 `ScannedFileRepository.findMissing` 提供明确入口。

## 6. SPI 如何反转依赖方向

扫描模块只发布领域无关的事件，并在 `src/main/java/com/mymedia/scan/spi/LibraryContentBuilder.java` 定义 `LibraryContentBuilder`：具体领域实现 `supports(LibraryDomain)`、`onFileDiscovered` 和 `onFileVanished`，再以 Spring bean 注册。这样依赖方向是“领域实现 scan 提供的接口”，而不是 `scan` 直接 import `video`、`image` 或未来的 `audio`；`src/main/java/com/mymedia/scan/spi/MediaKind.java` 也只提供 VIDEO、IMAGE、ARCHIVE 等粗粒度物理分类，不试图判断一个 MKV 是电影还是番剧。`src/main/java/com/mymedia/scan/LibraryScanner.java` 只发布 `ScannedFileDiscovered`、`ScannedFileVanished` 和 `LibraryScanCompleted`，没有具体语义实体的分支。

边界由 `src/main/java/com/mymedia/scan/package-info.java` 的 `@ApplicationModule(allowedDependencies = {"shared", "library", "jobs"})` 声明，并由 `src/test/java/com/mymedia/ModularityTests.java` 中的 `ApplicationModules.verify()` 在测试阶段强制检查；任何 scan 对具体领域模块的直接依赖都会使架构测试失败。加入音频域时，音频模块需要扩展允许的库域模型（例如在 `LibraryDomain` 增加 `AUDIO`）、新增自己的 `AudioContentBuilder implements LibraryContentBuilder` 并注册为 bean，自己的表和进度也留在音频模块；扫描遍历、对账、哈希、事件类型和 `scan` 模块本身都不需要修改。这种新增只接入既有 SPI，正是反转依赖带来的扩展点。

## 7. 为什么路径统一成正斜杠

磁盘访问必须使用当前平台的 `Path`，但数据库里的相对路径是跨平台的持久化值。`DirectoryWalker.toPortablePath` 不调用平台相关的 `Path.toString()`，而是逐段拼接并显式插入 `/`；`src/main/java/com/mymedia/scan/ScannedEntry.java` 的 `relativePath` 注释也把正斜杠作为契约。因此 Windows 上的 `电影\The Matrix.mkv` 和 Linux 上的 `电影/The Matrix.mkv` 在数据库、事件、改名比较和 API 输出中是同一个值，迁移媒体库或比较扫描结果时不会因为分隔符不同产生重复记录。物理根路径仍按操作系统保存和解析，只有相对于根目录的 `relative_path` 统一为正斜杠。
