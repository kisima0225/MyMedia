# 前端 Walkthrough

本阶段给 MyMedia 补上一个 Vue 3 单页前端，让计划 01–06 已经做完的全部后端能力——扫描、
播放、阅读、预览、刮削、搜索、收藏、分享、上传——都能在浏览器里演示和使用。19 个任务分
五段：地基（后端补口）、骨架（构建与外壳）、视频域、图片域、跨域与管理。全过程**没有新增
任何 Flyway 迁移**，也**没有给后端加任何新依赖**。

## 1. 做了什么

### 1.1 技术栈：Vue 3 + Vite + TypeScript，刻意不引入的三样东西

`frontend/` 是独立的 Vite 8.2.2 + Vue 3.5.41 + TypeScript 6.0.3 工程，由
`frontend-maven-plugin` 2.0.2 绑进 `mvn` 生命周期（下载 Node v24.19.0、`npm ci`、
`npm run test`、`npm run build`），构建产物落进 `target/classes/static/`，随 jar 单容器交付。

**不引入 UI 组件库**（不用 Element Plus / Naive / Vuetify）、**不引入 CSS 框架**
（不用 Tailwind）、**不引入 HTTP 客户端库**（不用 axios）。理由与后端「不引入无法解释的
中间件」是同一条：一个媒体库的界面元素就是卡片、网格、进度条、面包屑，套一个几百 KB 的
组件库既讲不出理由，又会把两套视觉语言压成组件库的默认样子；原生 `fetch` 足够用，且票据
与 401 处理本来就要自己写一层封装，引入 axios 只是多一层要理解的抽象。

### 1.2 媒体票据：让 `<video>`/`<img>` 也能带凭证

后端认证方案是 HTTP Basic（ADR-002），但浏览器的 `<video src>`/`<img src>` 无法携带
`Authorization` 头。计划 07 新增一条媒体票据链路解决这个问题，完整决策记录见
[ADR-008](../adr/ADR-008-媒体票据.md)。这里只说前端这一半：`api/ticket.ts` 维护一个
`TicketCache`（按 `expiresAt` 提前 30 秒判断是否需要续签），`api/media.ts` 的
`mediaUrl(path)` 是 async 的——这个不便是刻意保留的，它提醒调用方"这里有一次网络往返"；
`assetUrl(assetId)` 是同步版本，用**上一次签发**的票据，给 `<Cover>` 这种一屏几十张封面
的场景用，首屏渲染时若还没签过票据就返回空串，`<Cover>` 渲染占位，票据到手后响应式地补上。

### 1.3 两个域两套视觉语言

**主题：视频发光，图片反光。** 这不是修辞，是决定了每一个 CSS 令牌的物理隐喻：

- 视频卡片 `box-shadow` 是彩色外发光（琥珀色 `#ffb020`，"放映灯"），图片卡片是黑色落影
  （朱红 `#c0483a`，"印泥"）。视频域底色偏冷（`#08090e`），图片域偏暖（`#12100d`）。
- 实现方式是 CSS 自定义属性 + `[data-domain="video"]`/`[data-domain="image"]` 属性选择器：
  `AppShell.vue` 按路由 `meta.domain` 给 `<body>` 打标，一套令牌两套取值。全局搜索页把
  两段结果各自包一层 `data-domain`，是整套体系最能说明问题的一屏——同一屏上两个域看起来
  就是两种东西。
- 两个签名元素，各自是一处后端投入的可见回报：视频域进度条上的**雪碧图悬停预览帧**
  （计划 05 生成的 100 帧雪碧图 + WebVTT，`ScrubBar.vue` 用 `background-position` 换帧，
  零额外网络请求）；图片域每张书卡左缘的 **4px 书脊渐变**（两行 CSS，表达"图片域的单位是
  一本"这条核心主张）。
- 唯一的例外是阅读器：`ReaderView.vue` 完全抛弃暗色外壳，满幅铺纸色 `#f2ede3`、chrome
  全隐——这是全应用唯一的亮面，理由见下面 §2.1。

### 1.4 域内两套端点，不做共用抽象

`api/video.ts` 与 `api/image.ts` 分立，没有一个"媒体"公共接口。这是有意的：视频的
`groups`/`episodes`/续播位置与图片的 `readable`/`browsable`/子树导航是两套完全不同的语义
模型，勉强抽象出"通用媒体条目"只会得到一层 `if (domain === 'video')` 判断，而不是复用。
唯一的跨域交汇点是全局搜索（`GET /api/search`，`web` 模块）——结果分两段返回，不混排。

## 2. 为什么这样做

### 2.1 阅读器状态机独立成纯函数

`lib/reader.ts` 的 `next/prev/goTo/setMode/visiblePages` 完全不碰 DOM，只是
`ReaderState → ReaderState`/`ReaderState → number[]` 的纯函数。三个真正容易写错的地方——
双页模式下奇数总页数怎么对齐（末页单独一页还是留白）、`rtl` 阅读方向下"前进"要不要在视觉上
换成向左、连续滚动模式切回单页模式时索引怎么折算——全部是状态机内部的分支逻辑，跟组件树、
生命周期、事件监听完全无关。独立成纯函数意味着这些分支可以直接喂输入断言输出，不需要挂载
一个真实组件、不需要 mock `IntersectionObserver`。这也是本项目"组件渲染不写测试，只测纯逻辑
模块"这条约定的直接应用——`reader.ts` 是这条约定收益最大的一个例子。

阅读器整段抛弃暗色外壳、满幅铺纸色是刻意的冒险：暗框围着一页亮的漫画会产生光晕，长时间
阅读很难受；而这个视觉突变也让"从图片域的浏览页进了阅读器"这件事被身体直接感知到，不需要
读任何文字提示。

### 2.2 进度上报的节流

视频播放的 `timeupdate` 事件每秒触发约 4 次，直接拿来上报进度，两小时的片子就是三万多次
请求。`lib/throttle.ts` 把它压到 5 秒一次（`createThrottle`），阅读进度同理压到 2 秒
（翻页比连续播放稀疏得多，不需要压得那么狠）。节流之外还有 `flush()`，在三个时机被显式
调用：`pause`、`visibilitychange`（切到后台标签页）、组件卸载前——不这样做的话，关掉标签页
或暂停播放的最后几秒进度会因为还没到下一个节流周期而丢失，用户下次回来发现"进度倒退了
几秒"。

### 2.3 CSS 多列瀑布流，不是网格

视频域用等高 16:9 网格——视频封面天然是这个比例，裁切基本无损。图片域反过来用 CSS
`columns` 多列瀑布流，封面按原始比例不裁切：漫画/画集封面的长宽比天差地别，裁成统一尺寸
会把标题文字和角色脸切掉。这个不对称的选择和后端"视频域语义强、图片域组织自由"是同一条
判断——不为了视觉一致性牺牲内容完整性。多列瀑布流零依赖（原生 `column-count` + `break-inside:
avoid`），比引入一个瀑布流布局库更容易讲清楚为什么这样做。

### 2.4 字体：拉丁自托管，中文走系统栈

四套字体（Archivo 视频标题 / Literata 图片标题 / IBM Plex Sans 正文 / IBM Plex Mono 全部
数字）只打包**拉丁字形子集**的 woff2（8 个文件，共 13.8–24.3 KB），CJK 字符完全依赖操作系统
自带字体栈。完整 CJK 字体包体积在 5–15 MB 之间，对一个要求 `docker compose up` 离线可用的
自托管服务是不可接受的膨胀；而每个主流操作系统（Windows/macOS/Linux 桌面环境）都自带一套
过得去的中文字体，不需要额外下载。**绝不 `<link>` Google Fonts**——离线部署环境下这个请求
会失败或被墙，界面会静默退化成系统默认字体，排版全面走样,而且不会有任何错误提示，
比根本不请求更难排查。

### 2.5 凭证存 `sessionStorage` 而不是 `localStorage`

`client.ts` 把 Basic 凭证的 base64 编码存进 `sessionStorage`：关掉标签页就失效。这是一个
自托管服务，"同一台电脑给多个人共用"（图书馆终端、家庭共享设备）比"跨设备/跨会话同步登录
状态"常见得多——`localStorage` 会让上一个用户的凭证在浏览器完全关闭前一直留在磁盘上，对
共用设备场景是一个真实的隐私问题。相对的，阅读器的翻页模式/方向偏好（`lib/reader.ts` 的
`mode`/`direction`）用的是 `localStorage`——这是显示偏好不是身份凭证，理由完全不同：一个
习惯从右向左阅读的人不该每次开新标签页都要重新切一次方向。同一个浏览器存储 API，两种数据，
两种生命周期，不是随手选的。

## 3. 坑在哪

### 3.1 TypeScript 6.0.3 必须锁死，不能用 `latest`

npm 上 `typescript@latest` 现在是 `7.0.2`——Go 原生重写版，包内**不再导出 `./lib/tsc`
子路径**。而 `vue-tsc@3.3.11` 正是靠 `require.resolve('typescript/lib/tsc')` 启动，配
TS 7 会直接 `ERR_PACKAGE_PATH_NOT_EXPORTED` 崩溃。`vue-tsc` 的 `package.json` 里
peer 依赖只声明 `typescript: ">=5.0.0"`——**这个声明是过宽的，拦不住你**升级到一个它实际
跑不起来的大版本。实测过 5.9.3 通过、6.0.3 通过、7.0.2 崩溃。前端所有依赖因此一律精确
版本（`package.json` 不写 `^`/`~`），并提交 `package-lock.json`。

这条坑之外还有一条更普遍的教训：`npx vue-tsc --noEmit | tail -20` 会把退出码变成 `tail`
的退出码，几乎永远是 `0`——**类型错误会被静默吞掉**，CI/自动化判定一旦信了这个退出码，
一个类型错误的构建会被判定成功。所有前端命令的判定因此一律先重定向到文件、再单独读
`$?`：`npx vue-tsc -b --force > tsc.log 2>&1; echo "exit=$?"`。这不是这个项目独有的坑，
是任何把命令输出接进管道再判定退出码的地方都会踩到的通用陷阱。

### 3.2 `srcFor` 回调 prop 的设想最终没有落地，用另一条更简单的路径解决了同一个问题

计划文本原本设想让 `VideoPlayer.vue`/阅读器组件接受一个"地址构造函数"prop
（`srcFor: (fileId) => Promise<string>`），让 Task 16 的分享页能复用它们但走
`X-Share-Ticket` 而不是登录票据。执行到 Task 16 时重新核实后端源码发现：**分享链接的
媒体流端点对无密码链接完全不检查 `X-Share-Ticket`**（`ShareLinkService.resolveUnlocked`
只在 `passwordProtected` 为真时才验票据）。这意味着分享页最常见的用例——无密码分享——
根本不需要任何票据，`<video src>` 可以直接拼一个公开 URL 字符串。`VideoPlayer.vue` 因此
一行没改（它本来就接受 `src: string`）；只有 `PageView.vue` 需要一个小的可选
`srcOverride?: string` prop 让分享页跳过内部的 `mediaUrl()` 调用。这是"先读实现再动手，
而不是按计划文本的字面设想直接改"的一个直接例子——计划写在前面，实现时的真实约束往往
更细，答案也往往更简单。

### 3.3 上传分片大小必须读服务端响应，不能客户端自己定

`POST /api/upload/sessions` 的响应体里带一个 `chunkSize` 字段——这是服务端按
`mymedia.upload.chunk-size` 配置算好、随会话一起下发的。如果前端按自己猜的一个分片大小去
切文件，每一片的 `start`/`end` 偏移量都会和服务端的 `totalChunks`/校验逻辑对不上，
`PUT .../chunks/{index}` 要么整体失败要么把数据错位写坏。这类"客户端不能自己定、必须读
服务端权威值"的字段在这个项目里不止一处（分片大小是这一次，采样哈希算法是另一次），
共同的教训是：凡是涉及"客户端计算结果要能被服务端理解"的地方，先去读服务端权威实现，
不要凭常识猜一个看起来合理的默认值。

### 3.4 二进制分片不能走 JSON 的 fetch 封装

`api/client.ts` 里已有的 `request()` 对任何非 `undefined` 的 body 一律 `JSON.stringify`
并设 `Content-Type: application/json`。分片上传的 `PUT` 请求体必须是原始字节
（`Content-Type: application/octet-stream`，后端直接从 `HttpServletRequest.getInputStream()`
流式读取）——`JSON.stringify(someBlob)` 会把一个几 MB 的二进制切片错误地序列化成字符串
`"{}"`，前端毫无察觉地把错误数据发给了服务端。解法是新增一个专门发二进制的 `putBinary()`
函数，复刻 `request()` 里的认证头拼接与 401 处理，但完全绕开 `JSON.stringify`。

## 4. 本计划顺手关掉的三个缺口

1. **G13**：`video_group`/`collection` 一直没有封面生成逻辑（V10 建了外键但无写入方）。
   前端不等后端补这个逻辑，直接在展示层用条目自己的封面代偿——`VideoGroup` 没有映射
   `coverAssetId`，分组卡片回落到组内第一个条目的封面。
2. **G24（部分）**：`continueWatching`/`continueReading`/两个收藏列表原本在 `findByIds`
   之后不重新校验当前库访问权，库访问被撤销后这些列表仍会吐出条目信息。Task 3 关闭了
   四处（两个收藏 + 两个继续列表），每处都带了"撤销访问权后列表为空"的用例；
   `VideoProgressService.record` 故意没动（详见 preflight Ruling R3）——加校验会让约
   10 个既有测试用例一起改，判定为超出本任务范围的连锁改动，留给后续。
3. **一直没人发现的"继续观看渲染不出卡片"**：`VideoProgressController`/
   `ImageProgressController` 原本的继续观看/继续阅读端点只返回
   `{fileId, positionSeconds, durationSeconds, completed}`——没有标题、没有封面、连
   `itemId` 都没有，前端拿到这个响应根本渲染不出一张像样的卡片。这个缺口在计划 01–06
   的纯 API 阶段完全不可见（没有界面去渲染它），只有真正要画一张"继续观看"卡片时才会
   现出原形。Task 3 把这两个端点改成查询下推富化，返回 `ContinueWatchingEntry`/
   `ContinueReadingEntry`（标题、封面、进度、完成状态一次性给全）。

```powershell
Invoke-WebRequest -Uri "http://localhost:8080/api/libraries?ticket=<票据>" -Method GET
```

```bash
cd frontend
npx vue-tsc -b --force > tsc.log 2>&1; echo "exit=$?"; head -20 tsc.log
# 退出码必须来自这一行本身，不能来自后面接的任何管道
```

### 5.3 秒传对齐

```bash
npx vitest run test/sampledHash.test.ts
```
`sampledHash.ts` 与后端 `shared/SampledHash.java` 的算法逐字对齐——8 字节大端序长度
前缀 + （小文件整份／大文件首尾各 1MB）一次性 SHA-256，任何一处顺序或字节序写反，测试会
直接失败而不是等真实上传时秒传静默不命中。

## 6. 交付边界

- **带密码的分享链接不支持媒体流播放**——分享票据走请求头而不是 query 参数，给它开一条
  query 入口等于把凭证挪到一个本来就设计给到处转发的 URL 上，密码保护形同虚设。这是刻意
  的取舍，完整理由见 [ADR-008](../adr/ADR-008-媒体票据.md) 的"未做"一节。
- **图片分享里一个节点同时可读又可浏览时，分享页只展示阅读器不展示浏览视图**——分享场景
  下这个二选一被简化处理，登录后在库内浏览没有这个限制。
- **刮削候选队列没有候选封面**——`MetadataDto.CandidateResponse` 的后端契约本来就没有
  封面字段（候选搜索结果本身不含图片 URL），队列界面只显示标题/年份/来源/相似度分数。
- **`GET /api/scrape/queue` 与媒体库管理页的刮削器列都是逐目标/逐库查询**——在自托管
  规模（几个到几十个库/待确认目标）下代价可以接受，没有为此新增批量查询端点。
- **上传会话的本地续传记录用单一 `localStorage` key**——同时开第二个上传会覆盖前一个
  未完成会话的续传信息（不影响服务端数据，只是那次会话失去了界面上的断点续传入口，
  需要重新完整上传）。
- 组件渲染不写单元测试，只有纯逻辑模块（`lib/*.ts`）有 Vitest 覆盖——这是本计划从
  Task 5 起就定下的既定约定，不是本阶段的取巧。
- 本环境没有浏览器自动化能力，"跨浏览器与响应式核对"清单（视频拖动出现 206、雪碧图
  悬停预览、阅读器三种模式、响应式断点、键盘可达性、减弱动效、深层路由刷新）**没有做
  真实的 Chrome/Firefox 人工点击验收**，只做了类型检查/构建产物/纯逻辑单测三层静态验证。
  建议后续有真实浏览器环境时，按上面这份判据清单补一次人工点击验收。

这些都不是本阶段遗漏的工作，而是明确划在验收范围之外、留给后续按需处理的边界，详见
总览交接文档的已知遗留表（G25 起）。
