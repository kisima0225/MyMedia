# 预览与元数据 Walkthrough

本阶段把扫描得到的条目补成“打开就能用”的媒体库：视频用 `ffprobe` 探测技术参数，
用 `ffmpeg` 抽帧生成封面，再由 JDK `ImageIO` 生成缩略图；图片目录和 CBZ 取自然序的
首页生成封面。较长的视频额外生成一张默认 100 帧的雪碧图和一个 WebVTT 索引，供前端
在进度条上悬停预览。

元数据部分则把本地 NFO、外部提供者和文件名兜底组织成一条有顺序的链。高置信度结果
自动写回，中等置信度进入候选队列，找不到时仍保留文件名推断的可用条目。整个阶段的
目标不是“每个条目都必须被某个网站认领”，而是“外部服务不可用时，媒体库仍然可用”。

## 1. 做了什么

### 1.1 扫描后的数据流

```text
扫描事务提交
    ├─ VideoItemCreated / ImageNodeCreated
    │      ├─ preview: PREVIEW_GENERATE
    │      └─ metadata: METADATA_FETCH（库配置非空时）
    └─ LibraryScanCompleted
           ├─ preview: 补排没有 COVER 的活动文件/节点（单轮最多 500）
           └─ metadata: 补排仍是 PENDING 的条目（单轮最多 500）

PREVIEW_GENERATE
    ├─ VIDEO_FILE: ffprobe → 回填 video_file → 抽帧 COVER → ImageIO THUMBNAIL
    │                                  └─ 时长足够时排 SPRITE_GENERATE
    └─ IMAGE_NODE: 自然序首页 → COVER + THUMBNAIL

METADATA_FETCH
    └─ LocalNfo → 配置的外部提供者 → Filename 兜底
```

预览与元数据的事件监听器都在事务 `AFTER_COMMIT` 后执行，并用 `REQUIRES_NEW` 持久化
任务。这样 worker 不会在扫描事务提交前读取到半成品；任务本身的重试、租约和历史
仍然由 `job` 表负责。

### 1.2 派生资源和统一访问端点

`derived_asset` 只保存生成物的索引：资源种类、来源 `scanned_file`、相对路径、实际
宽高、文件大小和生成时间。封面、缩略图、雪碧图与 VTT 共享这一模型，访问统一走
`GET /api/assets/{id}`。端点沿来源文件所属媒体库校验访问权，无权、未知资源和物理
文件缺失都返回 `404`，不会泄露资源是否存在。

视频条目的 `PREVIEW_GENERATE` 会先探测再抽帧，因为抽帧点是时长的 10%。图片节点
不需要外部进程：散图目录读第一张图片，CBZ 读索引中的第一张页；CBZ 页面直接从
压缩包流式读取，绝不把整本解压到磁盘。

## 2. 为什么这样做

### 2.1 `derived_asset` 与那条迟到的外键

`video_item.cover_asset_id` 和 `image_node.cover_asset_id` 在领域表创建时就已经有了，
但当时预览模块还不存在，`derived_asset` 也还没有建出来。因此 V6 / V8 只能先保存
一个没有外键约束的列；V10 建好 `derived_asset` 后才补上四条外键：

- `video_item.cover_asset_id` → `derived_asset(id)`
- `video_group.cover_asset_id` → `derived_asset(id)`
- `collection.cover_asset_id` → `derived_asset(id)`
- `image_node.cover_asset_id` → `derived_asset(id)`

这是迁移顺序造成的真实依赖，不是遗漏。外键使用 `ON DELETE SET NULL`，所以可以直接
删除所有生成物索引而不先扫描所有引用。数据库会自动把封面引用置空，用户条目、播放
进度、阅读进度和手工元数据都保留。

路径分片使用**来源文件 id**而不是 `derived_asset.id`：来源 id 在写文件前就已经知道，
派生资源 id 则要插入数据库后才产生。实际路径形如：

```text
covers/37/1337-cover.jpg
thumbs/37/1337-thumb.jpg
sprites/37/1337-sprite.jpg
sprites/37/1337-sprite.vtt
```

同一个来源文件重新生成时会覆盖同一路径，数据库的
`UNIQUE (source_scanned_file_id, kind)` 则保证登记操作是幂等更新，不会积累孤儿行。

### 2.2 派生目录如何重建

清空派生资源时，先清数据库索引，再清磁盘目录：

```sql
-- 清空派生资源；所有 cover_asset_id 由外键自动置空
DELETE FROM derived_asset;
```

Git Bash：

```bash
rm -rf ./data/derived
```

PowerShell：

```powershell
Remove-Item -Recurse -Force ".\data\derived"
```

然后以已认证的管理员身份触发一次对应媒体库的扫描：

```text
POST /api/libraries/{libraryId}/scan
```

`LibraryScanCompleted` 的补齐监听器会把仍没有封面的活动文件或节点重新排入预览任务，
每轮最多 500 个。大库需要重复触发扫描，直到剩余队列排空；这是一条明确的批处理
边界，不把“单个监听器调用”误说成无限批量操作。

这条链兑现了“派生目录删光后可由任务队列全量重建，不碰用户数据”的承诺：生成物
可以丢，原始媒体和领域数据不能丢。

### 2.3 `CommandRunner` 为什么存在

`ProcessCommandRunner` 是 `ProcessBuilder` 的唯一实现，所有 `ffmpeg` / `ffprobe` 调用
都经过 public 的 `CommandRunner`：

```java
CommandResult run(List<String> command, Duration timeout)
```

这样不是为了抽象层数量好看，而是为了把两个问题隔开：

- `FfprobeParser`、命令行参数构造、WebVTT 几何计算都能用纯单元测试验证，不依赖本机
  是否安装 ffmpeg。
- 集成测试可以注入手写 `StubCommandRunner`，现场写一张真实 JPEG，让下游的 `ImageIO`
  也走真实路径；不引入 Mockito，也不把测试绑在外部二进制上。

进程实现同时启动虚拟线程读取 stdout 和 stderr，避免子进程因管道缓冲区写满而假死；
超时后会强制终止进程，而不是只停止等待。否则一个卡住的 ffmpeg 会一直占着任务租约。

### 2.4 `-ss` 为什么放在 `-i` 前

封面命令是：

```text
ffmpeg -y -ss <duration*0.1> -i <file> -frames:v 1 -vf scale=640:-2 -q:v 3 <out.jpg>
```

`-ss` 放在 `-i` 前，ffmpeg 可以快速 seek 到附近关键帧再开始解码；放在 `-i` 后，
通常要从头解码到目标时间再丢弃前面的帧。两种写法都可能成功生成图片，所以只看集成
测试的“文件存在”发现不了性能回归。`MediaCommandsTest` 直接断言 `-ss` 的位置，
把这个性能关键点固定成契约。

### 2.5 雪碧图为什么默认 100 帧、10×10

默认使用一张图、100 帧和 10×10 网格后，系统只需要维护一个雪碧图和一个 VTT；这些值
仍可由预览配置覆盖。不需要多图分页、跨图边界、按时长计算图数或处理最后一张残图。
帧间隔由 `fps = spriteFrames / duration` 得出（默认 `spriteFrames = 100`），VTT 再用时间比例
把配置数量的 cue 覆盖到整个视频时长。

`ffmpeg` 的 `scale=<spriteTileWidth>:-2`（默认 `160:-2`）会根据源视频比例计算实际高度，并调整为编码器喜欢的偶数。
因此 VTT 的 tile 高度不能在 Java 中凭配置重算，而要先用 `ImageIO` 读取生成结果，
再用实际雪碧图宽高除以配置的列数/行数计算 `#xywh`（默认列数为 10、行数为 10）。否则比例、
取整或以后更换编码参数都会让悬停区域错位。

## 3. 元数据链与边界

### 3.1 两套机制表达四级优先级

目标优先级是：

```text
用户编辑 > 本地元数据文件 > 刮削 > 文件名
```

这里没有另造一个数值 tier：

- **链顺序**负责“谁先尝试”：`LocalNfo → libraries.metadata_providers 配置顺序 → Filename`。
  高置信度的外部候选命中后立即停止，低置信度不直接写入。
- **`locked_fields`** 负责“谁不能覆盖”：用户编辑字段时同时加入锁定数组，之后任何
  NFO 或外部刮削都跳过这些字段。
- **`field_sources`** 只记录当前字段由谁写入，给界面展示，不参与下一次判定。

`FieldMergePolicy` 只有两条规则：刮削跳过锁定字段，且跳过空值，避免一次不完整的
外部响应把已有数据清空。用户编辑走 `applyUserEdit`，不经过这个过滤，因为用户就是
自己的权威。

例如，用户先通过：

```http
PUT /api/video/items/42/metadata
Content-Type: application/json

{"fields":{"title":"我的剪辑版","summary":"我写的简介"}}
```

标题和简介会写入 `locked_fields`。之后 NFO 或 TMDB 返回另一套 `title`，标题会被跳过；
如果返回了未锁定的 `releaseDate`，该字段仍可以更新。这样“重新刮削补齐新字段”和
“不覆盖用户明确改过的字段”可以同时成立。

JSONB 和 `TEXT[]` 仍全部由 `JdbcTemplate` 读写：`metadata`、`raw_metadata`、
`field_sources`、`locked_fields` 以及库上的 `metadata_providers` 不做 JPA 映射。图片
域没有 `release_date` / `rating` 列，它们和 `originalTitle` 一样落进 `metadata` JSONB，
对外仍还原为统一字段视图。

### 3.2 二元组 Dice 与 `pg_trgm` 三元组

提供者候选匹配使用字符二元组 Dice 系数：

```text
2 * |A ∩ B| / (|A| + |B|)
```

交集按多重集计算，并先去掉空白、标点和大小写差异。中文多数有效词组是两个字，
二元组的信息密度比三元组更合适；编辑距离则把“进击的巨人”和“巨人”的包含关系
看得过远，不适合这里的候选排序。

这和计划 06 的 PostgreSQL `pg_trgm` 不是重复建设：前者是应用层对外部候选做匹配，
后者是数据库端检索索引。一个服务候选置信度，一个服务本地查询，各自处在不同边界。

当前阈值是：

| 分数 | 行为 |
|---|---|
| `>= 0.8` | 取详情并自动应用，状态 `MATCHED` |
| `0.4 <= score < 0.8` | 写入 `scrape_candidate`，状态 `NEEDS_REVIEW` |
| 低于 `0.4` 或没有候选 | 使用 `FilenameProvider`，状态 `NO_MATCH` |

候选表用两个可空外键加 `CHECK` 约束保证恰好一个目标，避免多态 `(type, id)` 留下
无法由数据库约束清理的悬空行。用户确认候选时才取详情，因为搜索结果可能没有简介，
而多数中等分候选最终会被忽略；忽略操作清空候选并置 `NO_MATCH`。

### 3.3 404 与 429 的区别

外部提供者的 HTTP 状态不能简单按“非 2xx 都失败”处理：

- `404` 表示对方没有这个条目，是正常的“没找到”，返回空结果，让链继续尝试后续提供者。
- `401`、`429`、`5xx`、连接失败和超时表示提供者暂时不可用，转换为
  `ProviderUnavailableException`，目标置 `ERROR` 并交给任务队列退避重试。

如果把 404 当成 429，一个本来就不存在于数据库中的冷门条目会永远重试；如果把 429
当成 404，真正的外部故障又会被安静吞掉。`HttpProviderSupport` 还统一设置标识性
`User-Agent`、每个提供者的客户端限流，以及有限的连接和读取超时。

TMDB 没有 API key 时，`TmdbProvider.available()` 返回 false，resolver 安静跳过它，
不把配置缺失伪装成网络错误。搜索和详情使用 Spring 自带的
`ConcurrentMapCacheManager`，当前没有淘汰策略；缓存键的上界是媒体库条目数，若未来
接入更多提供者或长期运行内存增长明显，再单独评估缓存生命周期。

### 3.4 XXE：为什么默认禁用 DOCTYPE

`.nfo` 是用户放进媒体目录的不可信输入。若 XML 解析器允许 DTD 和外部实体，下面的
实体就可能尝试读取服务器上的文件：

```xml
<!DOCTYPE foo [<!ENTITY xxe SYSTEM "file:///etc/passwd">]>
```

`NfoParser` 设置 `disallow-doctype-decl=true`，同时关闭 XInclude 和实体展开。这里不是
“发现可疑标签后再拦截”的黑名单策略：合法的 Kodi/Jellyfin NFO 不需要 DTD，禁止
DOCTYPE 才是唯一正确的默认值。坏的 NFO 会被本地提供者安静跳过，后续提供者仍可接手。

### 3.5 依赖方向：为什么 scan 倒置、metadata 不倒置

`scan` 只处理目录遍历、采样哈希、对账和改名检测，物理工作与“这是电影还是漫画”
无关，所以由 `LibraryContentBuilder` SPI 让领域实现，换来新增领域不改扫描代码。

`metadata` 处理的是领域特定的外部协议：TMDB 只服务影视，Bangumi 的动画与书籍要用
不同 type，图片与视频的 NFO 字段也不同。把这些判断倒置到领域模块只会搬家，不会减少
判断，还会增加 SPI 和跨模块契约。于是 `preview` / `metadata` 单向依赖 `video` / `image`，
领域模块不认识它们；`ModularityTests` 用 `allowedDependencies` 强制这张图。

## 4. 坑在哪

### 4.1 Boot 4 的 Jackson 3

应用使用的是 `tools.jackson.databind.ObjectMapper` / `JsonNode`，不是 Jackson 2 的
`com.fasterxml.jackson.databind`。节点读取使用 `asString()` 和 `properties()`；解析异常
按 `Exception` 捕获，因为 Boot 4 这套 `JacksonException` 是运行时异常。计划 05 的 ffprobe、
任务载荷和提供者响应都按这个约定实现。

### 4.2 探测失败与抽帧失败不是同一种失败

ffprobe 失败通常说明文件暂时不可读、正在写入或存储盘不可用，因此预览处理器抛出异常，
让任务按既有退避机制重试。文件能被探测但抽不出帧时，重试通常不会改变内容问题，处理器
记录警告并成功结束，条目只是暂时没有封面。这避免坏视频把任务队列永久拖进重试。

### 4.3 图片节点的归档竞态

`ImageNodeCreated` 可能先于 `ARCHIVE_INDEX` 任务完成。归档节点没有直属页时不能把子树页
误当成本节点封面来源；图片预览生成器会等待归档索引就绪，再读取节点和首页。元数据侧
则可以直接使用节点保存的 `archiveScannedFileId` 定位 CBZ 本体，即使页表尚未填好，仍能
先尝试同目录 NFO 或文件名兜底。

### 4.4 真机验证的边界

`FfprobeSmokeTest` 是唯一直接启动真实 ffprobe 的测试。本机没有二进制时通过
`assumeTrue` 跳过，解析器、命令行和任务处理器仍有纯单元/桩集成测试覆盖。

Bangumi 的协议事实已用真实服务验证：无需鉴权，搜索是
`POST /v0/search/subjects?limit=N`，详情是 `GET /v0/subjects/{id}`，且搜索结果没有
`summary`。TMDB 端点形状按官方文档实现，由 JDK `HttpServer` 本地桩覆盖，**没有真机
验证**，不能在简历上写“对接并验证了 TMDB”。

## 5. 怎么自己验证

### 5.1 只验证真机 smoke test

```powershell
mvn -B -ntp test "-Dtest=FfprobeSmokeTest" "-DfailIfNoTests=true"
```

本机有 ffprobe 时测试会执行；没有时显示 skipped，不计为失败。

### 5.2 验证前 11 个任务和模块边界

```powershell
mvn -B -ntp test "-Dtest=ModularityTests,PreviewWiringTest,AssetControllerTest,VideoPreviewJobTest,ImagePreviewJobTest,SpriteJobTest,MetadataWriteBackTest,MetadataFetchJobTest" "-DfailIfNoTests=true"
```

需要运行任务的集成测试显式设置 `mymedia.jobs.enabled=true`，并用 Awaitility 等待具体
任务 id 的状态；不能用固定次数 `pollOnce()` 猜异步调度时序，也不能用跨测试共享的
全局 `job` 行数做断言。

### 5.3 从干净数据库验证迁移

```powershell
mvn -B -ntp test "-Dtest=FlywayMigrationTest" "-DfailIfNoTests=true"
```

这一步确认 V1 到 V11 在全新 PostgreSQL 17 容器中按顺序执行，尤其确认 V10 的封面外键
和 V11 的候选表没有修改已执行迁移的校验和。

### 5.4 最终全量验证

```powershell
mvn -B -ntp verify *> verify.log
$exitCode = $LASTEXITCODE
Write-Output "EXIT=$exitCode"
Select-String -Path "verify.log" -Pattern "Tests run:|BUILD" | Select-Object -Last 20
```

验收条件是退出码为 `0`、日志含 `BUILD SUCCESS`、Failures 和 Errors 都为 `0`。Windows
无法创建符号链接时，既有 `DirectoryWalkerTest` 可能按环境假设 skipped；这不是 Task 12
引入的失败，应在日志中单独记录。

## 6. 交付边界

本阶段没有为 `video_group` 和 `collection` 生成独立封面写入逻辑；V10 已为它们补上
外键，展示层可以使用第一个条目的封面作为代偿，这属于后续前端阶段的展示选择。
同样，补齐监听器的单轮上限、缓存无淘汰策略和图片域对所有活动节点排刮削任务都是
已知的工程边界，不在本阶段伪装成已经解决的能力。
