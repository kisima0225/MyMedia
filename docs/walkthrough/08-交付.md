# 交付 Walkthrough

计划 08 是最后一份，任务不是再加功能，而是把前七份做出来的东西变成**别人能跑起来、也能
听我讲明白的一个项目**。11 个任务分三段：A 一键演示（应用镜像 / compose 编排 / 演示资产

**这一段的验收判据与前七份不一样。** 前七份看的是测试数字（683 个后端用例 + 68 个前端
用例），这一段看的是命令的真实输出：镜像建不建得出来、`docker compose up` 之后浏览器里
有没有东西、`curl` 拿到的是不是 200。测试当然还是全绿的（段边界各跑过一次全量
`mvn -B -ntp clean verify`，683 + 68 全绿、`BUILD SUCCESS`，与计划 07 合并后的基线一字
不差），但绿不能证明"这个项目交付得出去"。

**全过程没有新增任何 Flyway 迁移**（编号仍停在 V16），**没有给后端加任何新依赖**，唯一
碰到的生产代码是 Task 9 的一个前端文件。

## 1. 做了什么

### 1.1 应用镜像：两阶段，运行阶段烘焙 ffmpeg

`Dockerfile` 是两阶段的。构建阶段 `maven:3.9-eclipse-temurin-25`：先只拷 `pom.xml` 跑一次
`dependency:resolve`（带 `-DskipFrontend=true`，这一步还没有 `frontend/` 目录，让前端插件
跑起来只会失败），把依赖固化成一层可复用的缓存；再拷 `src` 与 `frontend` 跑
`mvn -B -ntp -DskipTests package`。运行阶段 `eclipse-temurin:25-jre`：apt 装
`ffmpeg curl ca-certificates`，建非 root 用户 `mymedia`（uid 1000），产出固定路径
`/app/app.jar`、`/app/data/derived`、`/app/data/uploads`、`/media`，`HEALTHCHECK` 打
`/actuator/health`（`SecurityConfig.java:29` 上是 `permitAll`，所以健康检查不需要凭证），
`ENTRYPOINT ["java","-jar","/app/app.jar"]`。

实测数字，一个不修饰：基础镜像 `eclipse-temurin:25-jre` **478 MB**，装完 ffmpeg、拷进
69 MB 的 jar 之后 `mymedia:dev` 是 **1.35 GB**。计划原文预估的是"700–800 MB 量级"，
**差了将近一倍**。根因不是 Dockerfile 写错了什么，是 Ubuntu 的 `ffmpeg` 包不是精简安装——
它会把 `libavcodec`/`libavformat`/`libavfilter` 连同一整套 GNOME/GStreamer 相关库
（`glycin-thumbnailers` 之类）一起拉进来。**估计值与测量值差一倍这件事本身值得说**：
写计划时没人算得准一个 apt 包的传递依赖有多重，正确的做法是建完之后老实记下真实数字，
而不是回头把预估区间改宽装作猜对了。

ffmpeg/ffprobe 的真实版本是 `8.0.1-3ubuntu2`，bash 5.3.9，curl 8.18.0——这些都是
`docker run --rm --entrypoint <cmd> mymedia:dev` 逐个问出来的，不是从包名推的（为什么必须
加 `--entrypoint`，见 §3.4）。

### 1.2 compose：三个卷、健康检查串起来的依赖、一个跑完就退的引导服务

`compose.yaml` 里有三个服务。`postgres`（`postgres:17`，`pg_isready` 健康检查）；`app`
（`build: .`，`depends_on: postgres condition: service_healthy`）；`demo-seed`
（复用同一个 `mymedia:dev` 镜像，`depends_on: app condition: service_healthy`，
`restart: 'no'`，`entrypoint` 覆盖成 `/bin/bash /seed/bootstrap-demo.sh`）。

三个卷：`mymedia-pgdata`（必须备份）、`mymedia-derived`、`mymedia-uploads`。派生资源卷
可以整个删掉——`application.yml:56` 上就写着"独立于媒体库路径，可整个删掉重建"，删完之后
`PreviewBackfill` 会在下一次扫描结束时把没有封面的条目重新排一遍任务。这不是顺口的一句话，
是"派生资源是纯函数的产物、原始数据才是唯一真相"这条设计在运维层面的兑现。

媒体目录 `./data/media:/media` **挂成可写**，理由见 §2.2。

### 1.3 演示数据：清单 + 获取脚本 + 离线兜底，仓库里零第三方媒体字节

`seed/manifest.json` 是一份清单：8 条资产，每条带 `url`、`sha256`、`bytes`、`license`、
`attribution`、`target`。2 段 Blender 官方预告片（CC BY 3.0）+ 6 张葛饰北斋（公有领域，
其中前两张是同一幅《神奈川冲浪里》的两次不同数字化，色调有肉眼可见的差异——这是刻意保留
的两份来源，不是重复上传）。`seed/LICENSES.md` 是署名表。`seed/nfo/` 下是**我们自己写的**
`.nfo` 与 `metadata.json`，那才是仓库里唯一的"媒体元数据"。

三个脚本：`scripts/fetch-seed.sh` / `.ps1`（按清单下载、校验 SHA-256、现打 CBZ）、
`scripts/generate-seed-offline.sh`（不联网，用镜像里已有的 ffmpeg 现场合成占位媒体）。
两条链路是**互补而不是互斥**的：在线清单里根本没有"剧集"素材，`S01E01` 形式的三集演示
剧集**只能**来自离线生成器——所以最终验收跑在两条链路都跑过的混合状态上，而不是重置成
"纯在线"。

### 1.4 可解释性资产：ADR-009~015、README 重写、八张真实截图

`docs/adr/` 从 8 篇补到 15 篇。新增的七篇分两组产出（009–012：模块化单体 / PostgreSQL
选型 / 物理层与语义层分离 / 两个域的不对称组织模型；013–015：按领域切分 API / 不引入
Redis-ES-MQ / 虚拟线程）。**拆成两个任务是刻意的**：每篇都要回代码里取实证——类名、迁移
编号、行号、实测数字——七篇塞进一个任务必然注水成七段听起来都对的空话。

README 整篇重写，架构图、功能清单、路线图、ADR 索引、部署清单全部对齐当前代码（此前一直
写着"五个模块"，实际早已是 11 个）。`## 部署清单` 那张表关掉了 G14——
`MYMEDIA_SHARE_SECRET` 留空的后果（重启后带密码的分享链接要访客重新输密码）从"某人记得"
变成了一行写在表里的字，同一张表里还顺手把"媒体票据密钥刻意不配"这条对照写清楚了：
同一个 `shared.HmacSigner`，两种生命周期，一个必须配、一个不必配，理由各自独立成立。

`tools/screenshots/` 是一个独立的 npm 小工程（Playwright 锁 `1.62.1`），对着真跑起来的
demo 站点截了八张图落进 `docs/images/`。**八张全是真的**——不是占位图、不是骨架屏、不是
登录页。写计划时预判"执行环境大概率起不了浏览器，那就只交付脚本、绝不伪造截图"，实际
Chromium 在这台机器上真跑起来了。

## 2. 为什么这样做

### 2.1 运行阶段为什么是 `eclipse-temurin:25-jre`——以及计划给的理由为什么不成立

计划原文给的理由是两条：**"Temurin 官方没有 25 的 alpine 变体"**，以及**"ffmpeg 在 musl
上要自己编"**。写这一节时逐条实测，**两条都不成立**：

```
$ docker manifest inspect eclipse-temurin:25-jre-alpine   → exit=0（amd64 + arm64 都有）
$ docker manifest inspect eclipse-temurin:99-jre-alpine   → no such manifest（对照组）
$ docker manifest inspect maven:3.9-eclipse-temurin-25-alpine → exit=0
$ docker run --rm alpine:3 sh -c "apk update && apk search -e ffmpeg"
ffmpeg-8.1.2-r0
$ docker images eclipse-temurin --format '{{.Repository}}:{{.Tag}} {{.Size}}'
eclipse-temurin:25-jre        478MB
eclipse-temurin:25-jre-alpine 306MB
```

alpine 变体存在，Alpine 社区源里有现成的 ffmpeg 8.1.2，基础层还小 **172 MB**。

那么真正站得住的理由是什么？**只有构建阶段那一条**：`frontend-maven-plugin` 的
`install-node-and-npm` 会去 nodejs.org 下载官方 Node 二进制（`pom.xml:185-194`，
`node.version` = v24.19.0），官方 Linux 构建是 **glibc 链接的**，在 musl 上跑不起来，
而这个插件没有下载 musl 变体的能力。构建阶段因此必须是 glibc 发行版，这一条是硬的。

**运行阶段没有同样硬的理由。** 它只需要一个 JRE、ffmpeg 和 curl，jar 本身跨 libc。老实
说：换成 alpine 至少能省 172 MB（基础层差额），考虑到 Ubuntu 的 ffmpeg 拖着一整套
GNOME/GStreamer 库、而 Alpine 的包依赖链通常轻得多，实际能省的大概率不止这个数——但那部分
我没实测，不当成结论。所以这条留在账上：**理由不成立，结论碰巧还能自圆其说**（两阶段共用
同一条发行版血统，省掉一整类"构建期与运行期 libc 不同"的排查），而 1.35 GB 里可以省掉的
那一块是真实存在的。

这一条是本阶段最该老实交代的地方。项目里已经有过三次"计划文本写错、执行时实测纠正"的
先例（Task 1 的 `useradd` uid 冲突、Task 3 的 PowerShell 5.1 参数、Task 5 的
`CAST(? AS jsonb)` 而非 `::jsonb`），这是第四次，也是唯一一次**结论对但理由错**的。
理由错比结论错更值得写下来——结论错会被下一次运行揪出来，理由错会被原封不动地讲给面试官听。

### 2.2 媒体卷为什么不能挂 `:ro`——顺带讲清 `upload` 为什么依赖 `scan`

`./data/media:/media` 是可写的，`compose.yaml` 里专门写了注释解释为什么不能加 `:ro`。

Web 上传（P11）这条链路的最后两步是：把合并好的文件**落进媒体库根目录**，然后**触发一次
增量扫描**把它接进语义层。挂成只读，第一步就写不进去，整条 P11 直接废掉——而且失败得很难
看，前端会把几个 G 的分片全传完，最后在合并那一步报一个文件系统错误。

这条约束顺手解释了模块图上一条容易被问的边：`upload` 的 `allowedDependencies` 里为什么有
`scan`。`upload/package-info.java` 自己写着答案——两件事：秒传要查既有物理文件的指纹
（`ScannedFileHashService`），合并落库后要触发增量扫描（`ScanTrigger`）。同一份注释里还
写了它**不依赖** `video` 与 `image`：上传只负责把字节放到正确的目录里，"这是一部电影还是
一本漫画"由扫描链路照常判定。**这就是"物理层共享、语义层分域"（ADR-011）在上传这条链路上
的又一次体现**——上传能做到域无关，恰恰是因为物理层本来就是域无关的。

### 2.3 引导为什么用 shell + curl，而 `AdminBootstrap` 为什么写成 Java

`scripts/bootstrap-demo.sh` 用 `curl` 打项目自己的公开 API：建两个库
（`POST /api/libraries`）→ 配置本地刮削器（`PUT /api/libraries/{id}/metadata-providers`）
→ 触发扫描（`POST /api/libraries/{id}/scan`）。零生产代码。

原本想仿 `AdminBootstrap` 写一个 Java 版 `SeedBootstrap`，放弃了，理由是模块边界：这段
逻辑需要同时用 `library`（建库）与 `scan`（触发扫描），而现有 11 个模块**没有一个的
`allowedDependencies` 同时允许这两条边**（`scan` 能依赖 `library`，反过来不行；`upload`
两条都有但它是上传模块，把演示引导塞进去是纯粹的越权）。为一段演示逻辑去动模块图，代价
远大于收益——而且动完之后，`ModularityTests` 里那份被刻意收紧过的依赖声明就不再表达
"真实的架构约束"，而是表达"架构约束加上一次为了方便开的口子"。

**对照 `AdminBootstrap`（`src/main/java/com/mymedia/user/AdminBootstrap.java`）**：它做的
事形式上一模一样——首次启动时创建初始账号、已存在则跳过、因此重启安全——但它只碰 `user`
一个模块（`UserRegistrationService` + `UserAccountRepository` + `UserRole`，全在包内），
写成一个 `ApplicationRunner` 是最自然的形态，不需要跨任何边界。

**同一个问题，两种答案，差别只在于跨了几个模块。** 这个对照比任何一句"我很重视模块边界"
都有说服力：边界真的在决策里起了作用，而不是一个贴在 `package-info.java` 上的装饰。

### 2.4 版权纪律怎么变成机器可执行的

"不放别人的媒体文件进仓库"是一条纪律，纪律靠自觉就会失守。这一段把它落成两个可判定的点：

**第一个是 `.gitignore`。** 第 24–26 行的 `media/`、`derived/`、`uploads/` 三条规则匹配
**任意层级**的同名目录，所以 `data/media/` 天然被忽略——不是因为有人记得，是因为 git 自己
拦。判据是一条命令：

```
$ git check-ignore -v data/media/video
.gitignore:24:media/    data/media/video
```

它同时回答了"被忽略了吗"和"被哪条规则忽略的"。核对一次的成本是几秒钟，而它拦住的是一类
不可逆的错误——媒体文件一旦被提交，就永远留在 git 历史里，`git rm` 删不掉。

反向核对同样是一条命令：

```
$ git -c core.quotepath=false ls-files | grep -iE "\.(mp4|mov|mkv|jpg|jpeg|png|cbz|zip)$"
docs/images/01-视频首页.png … docs/images/08-分片上传.png
```

**版本库里唯一的二进制媒体是我们自己截的八张图。** 零第三方字节，这是可执行的断言，
不是承诺。（`core.quotepath=false` 那个开关是必要的：不加它，git 会把中文路径转义成
`\350\247\206...`，正则里的 `.png$` 匹配不上结尾带引号的转义形式，一条本该报警的检查会
静默返回空——这类"检查跑了、但什么也没检查到"的假阴性，比不做检查更危险。）

**第二个是 SHA-256。** 清单里每条资产都带哈希，`fetch-seed.sh` 下完先校验再落位
（下载到 `.part`，校验通过才 `mv`）。这让"下到的东西是不是清单里那个"从一个信任问题
变成一个可判定的问题——上游换了文件、CDN 返回了错误页、传输被截断，三种情况都会在校验
那一步当场失败，而不是等到扫描时冒出一个诡异的解码错误。

### 2.5 凡是打别人的服务器，都要自带节流

写计划时实测 Wikimedia Commons 的可用性，**连续四个 `curl -I`，后两个直接返回
`429 Too many requests`**。四个请求就被限流了。

`fetch-seed.sh` 因此每下完一条 `sleep 2`（`INTERVAL=2`），并带一个标识性 User-Agent
（`MyMedia-seed/0.1 (+https://github.com/…)`，见 `seed/manifest.json` 的 `userAgent` 字段）。
匿名高频爬是给自己招风控。

**这不是一条新判断，是同一条判断的第二次应用。** 后端刮削链早就有一模一样的东西：
`application.yml:68` 的 `mymedia.metadata.min-request-interval: PT1S`（注释就写着
"客户端侧限流"），实现在 `metadata/HttpProviderSupport.java:110` 的 `throttle()`，
方法注释一句话说完了理由——**"别指望对方的 429 来教你做人：等到被限流时，这一轮扫描的
几百个请求已经发出去了"**。同一个 yml 文件第 67 行还有一条 `user-agent`，注释是
"匿名爬对方是给自己招风控"。

一条判断在后端 HTTP 客户端与一个 shell 获取脚本上各表达一次，两处的形态完全不同（一个是
`synchronized` 门闩 + 时间戳表，一个是 `sleep 2`），但底下是同一句话：**凡是打别人的
服务器，节流要在自己这边做，不能等对方教你。**

### 2.6 离线兜底为什么不打 CBZ

`generate-seed-offline.sh` 造的图片素材是**一个 12 页的散图目录**，不是 CBZ。脚本第 30 行
的注释写着理由：**"不打 CBZ：容器里没有 zip，而图片域本来就原生支持散图目录"**。

这不是"少做了一个功能"，是选了一条不需要新依赖的路。要在容器里打 CBZ，要么往镜像里再装
一个 `zip`（为了一段离线兜底逻辑给运行镜像加一个包，1.35 GB 上再加一层，还得在 Dockerfile
里解释它为什么在），要么绕道 `python3`（`fetch-seed.sh` 在宿主机上就是这么兜底的，但运行
镜像里也没有 python）。而图片域的 `image_node.source_kind` 本来就有 `DIRECTORY` 与
`ARCHIVE` 两种取值（`V8__image_domain.sql`），散图目录是**一等公民**而不是降级形态——
离线演示要展示的"这是一本可读的书"，散图目录一点不打折地展示得了。

顺带一提，在线路径（`fetch-seed.sh`）**是**打 CBZ 的，因为它跑在宿主机上、有 zip 或
python3 可用。所以最终的演示库里两种形态都有：Task 4 实测扫出三个可读叶子节点，页数
12/6/6——12 页那个是离线散图目录，6 页的两个一个是在线散图目录、一个是 CBZ
（`sourceKind: "ARCHIVE"`）。两条 `source_kind` 分支在演示数据里都真的被走到了。

### 2.7 截图工具为什么在 `tools/` 而不是 `frontend/`

`frontend/package.json` 的依赖表短得刻意：运行时只有 `vue` / `vue-router` / `pinia`
三个，devDependencies 六个（vite、vitest、vue-tsc、typescript、`@vitejs/plugin-vue`、
`@types/node`）。不引组件库、不引 CSS 框架、不引 axios——这是计划 07 定下的、能逐条讲出
理由的克制。

Playwright 是一个下浏览器二进制、装完几百 MB 的东西。把它塞进 `frontend/devDependencies`
的后果是：**应用的依赖树里从此有一个和应用毫无关系的东西**。别人克隆仓库跑 `npm ci` 会
莫名其妙多等几分钟；`mvn` 生命周期里的 `npm ci`（`pom.xml:196`，绑在 `generate-resources`）
会在**每一次构建镜像时**都拖一遍它；而它产出的东西是 README 里的图片，跟能不能跑起来
没有一点关系。

所以它在 `tools/screenshots/`：自己的 `package.json`、自己的 `package-lock.json`、自己的
README，**不进 `frontend/`，也不接进 Maven 生命周期**。判断标准是一句话——**产文档资产的
工具不该出现在应用的依赖树里**。同一条标准也解释了为什么 `.dockerignore` 里挡掉了
`tools/` 和 `docs/`：它们既不参与构建，也不该进镜像。

## 3. 坑在哪

### 3.1 `-DskipTests` 关不掉前端测试

镜像构建阶段那一行是 `mvn -B -ntp -DskipTests package`，日志里照样滚过
`Test Files 8 passed (8) / Tests 68 passed (68)`。

原因不玄：`-DskipTests` 是 **surefire** 的开关，只管后端单元/集成测试；而 Vitest 是
`frontend-maven-plugin` 的一个 execution（`pom.xml:204-210` 的 `npm-test`，
`<arguments>run test</arguments>`），绑在 **`generate-resources`** 阶段，跟 surefire
毫无关系。同一个插件的另外两个 execution（`npm-ci` 在 196 行、`npm-build` 在 212 行）
也都绑在 `generate-resources`。要关它得用 `-DskipFrontend=true`（`pom.xml:20` 定义的属性，
182 行的 `<skip>` 读它）——但那会连前端构建一起关掉，产出一个没有界面的 jar。

**所以镜像构建时前端 68 条测试是照跑的，而且这是对的**：前端产物要进 jar，跑一遍它的测试
不算浪费。真正被跳过的是后端测试，理由完全不同：后端集成测试走 Testcontainers，要连
Docker 守护进程，而**构建容器里没有 Docker**（除非挂 socket 进去做 DinD，那是给自己找
一整类新故障）。

这条坑的普遍形态是：**"跳过测试"不是一个统一的开关**，它是每个测试框架各自的开关，而
Maven 的阶段绑定决定了谁能被谁关掉。判断"这条命令到底跳过了什么"的唯一可靠方式是读
`pom.xml` 里每个 execution 的 `<phase>`，不是凭 `-DskipTests` 这个名字的字面意思。

### 3.2 `.dockerignore` 里最重要的两行

```
frontend/node_modules/
.frontend-toolchain/
```

这两个目录在开发机（Windows）上装的是 **Windows 二进制**：`.frontend-toolchain/node/` 下
是 `node.exe`，`frontend/node_modules/` 里有一堆平台相关的 `.node` 原生模块与
`@rollup/rollup-win32-x64-msvc` 之类的可选依赖。漏进 Linux 构建阶段，`COPY frontend ./frontend`
会把它们原样搬进容器，然后 `npm ci` 要么跳过安装（因为 `node_modules` 看起来已经在了）、
要么装出一个混合状态，最终以 **`node: not found`**、`Exec format error`、
`Cannot find module @rollup/rollup-linux-x64-gnu` 这类**完全指错方向**的错误崩掉。

排查它极费时间，因为报错发生在容器里、跟本机能不能跑没关系，而人的第一反应总是去查
Node 版本、查网络、查 npm 源——没有一条是对的。

判据是构建日志开头那一行：

```
#8 transferring context: 34.73kB 0.1s done
```

34 KB。`node_modules` 在本机是几百 MB，只要它进了上下文，这个数字会是三位数的 MB。
**先看这一行再看别的**——它一秒钟就能排除掉一整类最难查的失败。

（`.dockerignore` 里另外几条是同一类判断的延伸：`data/`（几百 MB 演示媒体，构建阶段完全
用不到）、`target/`（本机构建产物，会和容器里的产物打架）、`docs/`/`README.md`/`tools/`
（文档与工具，既不参与构建也不该进镜像）。）

### 3.3 基础镜像自带一个 `uid=1000` 的 `ubuntu` 账号

计划原文的 Dockerfile 里有一行 `useradd --system --uid 1000 ... mymedia`，第一次
`docker build` 就挂了：

```
#17 0.266 useradd: UID 1000 is not unique
#17 ERROR: ... did not complete successfully: exit code: 4
```

`eclipse-temurin:25-jre` 的底层是 Ubuntu 26.04 LTS，较新的 Ubuntu 云镜像惯例地自带一个
`ubuntu:x:1000:1000:...` 账号。修复是先 `userdel -r ubuntu` 再建自己的（Dockerfile 里
现在那两行，附带一段解释为什么），删得很干净——没有遗留账号、组或 home 目录。

要说的不是"我踩了一个坑"，是**为什么会踩到**：uid 1000 是"第一个普通用户"的约定俗成值，
选它是为了让 Linux 宿主上 `chown -R 1000:1000 data/media` 这条运维指令能直接对上
（README 部署清单里就是这么写的）。约定俗成值的另一面就是**别人也会用它**。凡是往一个
不受自己控制的基础镜像里塞固定 uid/gid/端口/路径的地方，都要先问一句"这个位置是不是已经
有人了"。

（副作用：`mymedia` 的 gid 是 999 不是 1000——原有的 `ubuntu` **组**没被 `userdel -r`
删掉，`useradd --system` 另分了一个。接口约定里只承诺 uid，不影响任何下游，但这是那种
"实测输出和预期差一个数、必须解释清楚才能往下走"的地方。）

### 3.4 只有 `ENTRYPOINT` 没有 `CMD` 时，`docker run <镜像> <命令>` 不执行那个命令

计划原文给的验证命令是 `docker run --rm mymedia:dev ffprobe -version`。它**看起来跑通了**
（有输出、退出码正常），实际执行的是 `java -jar /app/app.jar ffprobe -version`——因为
exec-form 的 `ENTRYPOINT` 会把 `docker run` 后面的参数**追加**上去，而不是替换掉；两个
多余参数被 Spring Boot 忽略，应用照常启动到 Flyway/Hikari 阶段才因为连不上 Postgres 退出。

**这是一次完美的假阳性**：命令有输出、有退出码、看起来在验证 ffmpeg，实际一个字节都没碰到
ffmpeg。正确的写法是 `docker run --rm --entrypoint ffprobe mymedia:dev -version`。

这和计划 07 §3.1 记的那条（`npx vue-tsc --noEmit | tail -20` 会把退出码变成 `tail` 的 0，
类型错误被静默吞掉）是同一类错误的两种形态：**验证命令本身没有被验证过**。判据是问一句
"如果被验证的东西根本不存在，这条命令会不会失败？"——如果答案是"不会"，这条命令就不是
一个判据。

### 3.5 空的 `metadata_providers` 会把 `scrape_status` 永久钉死在 `NOT_APPLICABLE`

引导脚本第一版是"建库 → 触发扫描"，跑完之后 `.nfo` 里写的中文简介一个字都没进条目。

根因在 `MetadataEventListener`：条目**被创建的那一刻**就去看所属库的
`libraries.metadata_providers`（`V3__libraries.sql:7`，`TEXT[] NOT NULL DEFAULT '{}'`），
空数组就把 `scrapeStatus` 直接定成 `NOT_APPLICABLE`——**而这是终态**。
`itemsPendingScrape` 只查 `scrape_status = 'PENDING'`，事后再配 provider、哪怕再扫一遍，
也不会回头认领已经定型的条目。`MetadataResolver` 的 javadoc 早就写明这是设计意图
（ADR-005 规则 2：空数组的库"连任务都不排，界面零刮削噪音"，"不把配置修改伪装成回溯式
取消"），只是没人把它和"演示引导的步骤顺序"联系起来。

修复是在建库与扫描之间插一步：`PUT /api/libraries/{id}/metadata-providers`，
`{"providers":["LocalNfo"]}`。只启用本地刮削器，不加 Bangumi/TMDB——保住"引导不需要任何
API key"这个目标。

**这条值得记进"已实测验证的事实"，因为它是一条顺序约束，而顺序约束不会自己暴露。**
反过来做（先扫描再配 provider）不会报错、不会有警告日志，只会安静地留下一个永远不刮削的
库。任何"某个配置必须在某个事件之前就位"的设计，都欠一句写在能被读到的地方的话。

### 3.6 PowerShell 5.1 与 CRLF shebang

项目所有者的实际环境是 **Windows PowerShell 5.1**（`$PSVersionTable.PSVersion` 实测
`5.1.22621.6060`），两条实测出来的限制：

1. `Invoke-WebRequest` **没有** `-MaximumRetryCount` / `-RetryIntervalSec`——这两个参数
   PowerShell 6+ 才有。计划模板里写了，原样跑直接报错。改成手写重试循环。
2. `.ps1` 源码**没有 UTF-8 BOM 时，5.1 按系统 ANSI 代码页解析源码**，脚本里写死的中文
   字符串字面量会乱码。加 BOM 解决。

还有一条更隐蔽的：Write 工具在这台机器上把新建的 `.sh` 文件落盘成 CRLF，加上仓库
`core.autocrlf=true`，shebang 会变成 `#!/usr/bin/env bash\r`，在 Linux 容器里报
`env: 'bash\r': No such file or directory`。修复是加了一个只锁 `scripts/*.sh` 的
`.gitattributes`（`text eol=lf`）——仓库此前**没有任何 `.sh` 文件**，所以这是第一次
撞上这个坑，也是为什么以前七份计划都没遇到过。

### 3.7 `container_name` 是固定字符串，同机多 worktree 会撞

`compose.yaml` 给三个服务都写了固定的 `container_name`（`mymedia-app` / `mymedia-postgres`
/ `mymedia-demo-seed`），而 compose 默认的容器命名是带项目前缀的。后果：**同一台机器上这份
compose 的多个 worktree 副本会在容器名上互撞**：

```
Error response from daemon: Conflict. The container name "/mymedia-postgres" is already
in use by container "79cb8c6c2439..."
```

Task 2 执行时就撞上了另一个 worktree（`D:\MyMedia`）遗留的已停止容器。固定名字的收益是
`docker logs mymedia-app` 这种命令可以照抄进文档，不必先 `docker compose ps` 查一遍随机
后缀；代价就是这条。**这是已知代价而不是缺陷**，但同机并行跑两份栈之前要知道它。

### 5.4 `.dockerignore` 真的生效

```bash
docker build -t mymedia:dev . > build.log 2>&1; echo "exit=$?"
grep "transferring context" build.log
```

## 6. 交付边界

- **`docker compose up` 之后的演示数据来自哪条链路，取决于跑没跑获取脚本**：不跑的话
  `data/media/` 是空的，两个库会被建出来但扫不到任何东西——这不是故障，是没有内容。
  在线获取要网络，离线兜底要本机或容器里的 ffmpeg。两条链路互补，剧集素材**只有**离线
  生成器有。
- **没有 CI**：spec §2 非目标明写"公网部署 / CI 自动部署"不做。在 runner 上跑
  Testcontainers 构建十几分钟，换一个绿徽章，对"这个项目怎么交付"不产生任何新答案。
- **没有 TLS、没有反向代理配置**：应用只监听 8080。README 部署清单里写了这一条，
  实现留给部署者——ADR-002 也说了 Basic 认证必须在 HTTPS 下部署才安全，而项目的交付形态
  是本机 compose，不涉及公网。
- **条目详情页目前不显示简介**（`ItemDetailView.vue` 硬编码"暂无简介"，不调元数据接口）。
  `.nfo` 的简介确实端到端打通了，但要在 `/admin/metadata/video/{id}` 那个"编辑元数据"页
  才看得到。这是计划 07 留下的既有范围边界，不是本阶段引入——**但人工验收时若只看条目
  详情页，会误判"元数据没生效"**，所以写在这里。
