# 视频域 Walkthrough

本阶段把扫描得到的物理文件提升为可供用户浏览和播放的语义目录。视频域把一部作品建模为 `VideoItem`，把可选的季/分册建模为 `VideoGroup`，把实际文件建模为 `VideoFile`；`VideoFolder` 只是按磁盘目录生成的导航索引。物理层的 `scanned_file.id` 仍然是文件的稳定身份，因此改名不会丢失语义层数据和播放进度。

## 1. 条目 API 与访问控制

`VideoCatalogController` 保持 package-private，和视频模块已有的 Web 控制器一样，不把控制器类暴露为跨模块 API。对外暴露的是 HTTP 路由和 public 的 `VideoCatalogDto` records：

| 方法 | 路径 | 返回值 |
|---|---|---|
| `GET` | `/api/video/items` | 所有可访问视频库中的 `ItemSummary` |
| `GET` | `/api/video/items/{id}` | `ItemDetail`，包含条目、分组和文件 |
| `GET` | `/api/video/items/{id}/episodes` | 该条目下按目录顺序排列的 `FileSummary` |

列表先由 `UserQueryService` 找到当前用户，再调用 `LibraryAccessService.accessibleLibraries`，只保留 `LibraryDomain.VIDEO`，最后按库查询条目。详情和 episodes 先由 `VideoCatalogService.getItem` 查出条目，再按条目的 `libraryId` 调用 `canAccess`。条目不存在，或用户没有所属媒体库的权限，都沿用现有 `NotFoundException`，由全局异常处理器返回 `404`，而不是返回 `403` 泄露资源存在性。管理员的隐式全库权限也因此复用同一套访问服务。

## 2. HTTP Range 请求的完整语义

流式端点是 `/api/video/stream/{fileId}`。文件长度为 `N` 时，Range 的两端都是闭区间：`bytes=start-end` 同时包含 `start` 和 `end`，所以响应长度是：

```text
end - start + 1
```

例如 `Range: bytes=0-9` 读取 10 个字节，而不是 9 个。当前实现只产生单个连续响应；多个 range 按项目既定决策合并为最小起点到最大终点，不返回 `multipart/byteranges`。

- `206 Partial Content`：Range 语法正确且至少有一个可满足的区间时返回，表示响应体只是所选 representation 的一部分。
- `Content-Range: bytes start-end/N`：说明本次发送的闭区间和完整文件长度。例如文件长 100000 字节时，`0-9` 的值是 `bytes 0-9/100000`。
- `Accept-Ranges: bytes`：服务端声明该资源支持按字节请求。完整的 `200`、部分的 `206` 和不可满足的 `416` 响应都带这个声明；完整响应还带 ETag 和准确的 `Content-Length`。
- `416 Range Not Satisfiable`：Range 语法正确，但所有区间都落在文件之外，或没有可发送的字节。例如长度为 100000 的文件请求 `bytes=100000-`。响应带 `Content-Range: bytes */100000`，表示已知完整长度但没有可满足区间。

三种常见写法的解析方式不同：

```text
bytes=100-199  # 第 100 至 199 字节，共 100 字节
bytes=100-     # 从第 100 字节到 N-1
bytes=-500     # 最后 500 字节，即 max(0, N-500) 到 N-1
```

`bytes=-500` 的数字是后缀长度，不是起点；如果文件短于 500 字节，起点钳制为 0。没有 Range，或 Range 语法无效时，服务端返回完整的 `200`。只有语法有效但越界时才返回 `416`。

## 3. `If-Range` 解决什么问题

`If-Range` 把“断点续传”与“资源版本校验”绑定起来。客户端可能已经拿到旧版本文件的前 1000 字节，随后连接中断；如果它用旧 ETag 请求：

```http
Range: bytes=1000-
If-Range: "old-version"
```

而服务端磁盘上的同一路径已经被替换，当前 ETag 变成了 `"new-version"`，服务端若无条件执行 Range，就会返回新文件的尾部 `206`。客户端把旧文件头和新文件尾拼在一起，虽然长度看起来正确，内容却已经损坏。

因此服务端只有在 `If-Range` 与当前强 ETag 相等时才使用 Range；不相等、格式不认识或日期证明资源已经更新时，忽略 Range 并返回完整的 `200`，让客户端丢弃旧片段重新得到一个一致的 representation。当前实现也接受合法的 HTTP-date：只有当前文件 mtime 不晚于该日期才继续部分响应；弱 ETag 不能作为 Range 的可靠版本校验。

## 4. 为什么语法错误的 Range 返回 200 而不是 400

`Range` 是 GET 的可选请求修饰字段，不是请求行或消息 framing 的必要语法。RFC 9110 §14.1 允许服务端忽略不能识别或无效的 Range 字段；忽略后请求仍然是一个普通的 GET，因此发送完整 representation 的正常结果是 `200 OK`，而不是把整个请求判为 `400 Bad Request`。这样客户端即使生成了不兼容的 Range，也仍能得到可用的文件。

这里必须区分两种错误：

- `bytes=abc-def`、缺少 `=`、未知 unit 等是 Range 语法错误，当前 `RangeParser` 让它退化为完整响应，返回 `200`。
- `bytes=999999-` 在文件只有 100000 字节时语法完全正确，只是没有任何可满足字节；这时按 Range 语义返回 `416` 和 `Content-Range: bytes */100000`。

这也是为什么不能把所有解析失败都简单映射成 `400`：那会把“可忽略的可选修饰字段错误”和“请求本身无法理解”混为一谈。

## 5. `FileChannel.transferTo` 为什么叫零拷贝

普通实现通常是：先把文件读到 Java 堆上的 `byte[]`，再把这个数组写进 HTTP 输出流。数据至少要经过“文件/内核页缓存到用户态堆”和“用户态堆回到内核 socket 缓冲区”两次边界拷贝，堆缓冲区还带来额外的分配和 GC 压力。

`FileChannel.transferTo(position, count, sink)` 把文件区域和目标 channel 直接交给底层 NIO/操作系统。在支持 `sendfile` 等机制的平台上，数据可以在内核路径中从文件缓存转发到 socket，绕过 Java 堆，省掉上述两次用户态往返。因此它被称为“零拷贝”，准确含义是避免应用层显式的数据拷贝，并不保证任何操作系统上物理上绝对没有一次复制。

控制器在循环中处理 `transferTo` 的短写：每次只推进实际传输的字节数；连续零进度达到阈值后，才退回有界的 direct `ByteBuffer` 读写，避免某些文件系统或 channel 实现返回 0 时响应在声明的 `Content-Length` 下静默截断。Spring 的虚拟线程配置则适合这个以文件和网络阻塞 I/O 为主的路径，但不改变 Range 的字节语义。

## 6. `structure` 为什么不由 `item_type` 推导

两个字段描述的是不同维度：`item_type` 是作品的语义类型，例如 `MOVIE`、`SERIES`；`structure` 是当前文件组织方式，是直接挂文件的 `FLAT`，还是经过季/分册分组的 `GROUPED`。如果从类型推导结构，就无法表达“作品是什么”和“文件怎么存”同时成立的情况。

一个真实例子是《指环王：护戒使者》加长版的双碟发行：它仍然是一部 `MOVIE`，但实际媒体文件可以按 `Disc 1`、`Disc 2` 分成两个连续部分，所以同一个条目可以是 `MOVIE` + `GROUPED`。同样，电影的 1080p、4K、花絮也可能是多个 `VideoFile`，而不是把作品错误地改成剧集。扫描器根据实际季/集或目录组织提升 `structure`，未来手工整理也可以改变它。

## 7. 文件名解析为什么永不抛异常

文件名是用户已有的外部数据，可能没有年份、没有季集标记、只有一个非法或不完整的标记，甚至路径本身为空。根据 spec §7.2 规则 1，没有刮削也必须完全可用，所以文件名解析只能是增强，不能成为导入成功的前置条件。

`VideoFilenameParser` 分层尝试文件名中的季集、目录中的季号、独立集号、年份和画质。每层失败只让对应字段保持 `null`；整数转换使用 `parseIntOrNull` 捕获 `NumberFormatException`。清洗标题后如果结果为空，会依次回退到最近的非季目录名、原始文件名，最后使用 `Untitled`，所以不会把空标题传给语义层。最差情况下，扫描仍会创建一个 `SINGLE_VIDEO`、`FLAT` 条目，用户可以浏览和播放它，之后再通过可选的 NFO 或刮削补元数据。

这个保证比“尽可能多猜字段”更重要：解析器猜错只会产生可修正的元数据，解析器抛异常则会让一个本来可播放的文件完全消失。

## 8. 物化路径 vs 递归查询

`video_folder` 同时保存 `parent_id` 和包含自身 id 的物化路径，例如：

```text
/
/1/
/1/17/
/1/17/93/
```

面包屑请求拿到 `/1/17/93/` 后，`MaterializedPath.ancestorIds` 可以直接得到 `[1, 17, 93]`；`VideoBrowseService` 用一次 `findAllByLibraryIdAndIdIn` 取回这些节点，再按 id 顺序在内存中重排。因此它不需要为每个父节点发一次查询，也不需要逐层递归，层数增加不会产生 N+1 查询。子树查询也可以使用带索引的 `LIKE '/1/17/%'` 前缀扫描。

代价是移动子树时不能只更新被移动节点的 `parent_id`：该节点及全部后代的路径前缀都要从旧前缀替换为新前缀。这会产生与子树大小相关的写放大、锁竞争和索引维护成本，移动期间还要保证路径和父子关系的一致性。`MaterializedPath.rewrite` 为数据库端的一次前缀替换准备了纯逻辑操作；当前视频域主要使用它读目录和面包屑，真正的移动场景需要在后续计划中补齐对应事务。

## 9. 自然排序为什么不能把数字解析成 `long`

文件名中的数字不一定落在 Java `long` 的范围内。`long` 最大值是 `9223372036854775807`，而文件名中的 20 位数字 `12345678901234567890` 用 `Long.parseLong` 会直接抛出 `NumberFormatException`。即使暂时没有这么大的集号，排序工具也不应因为一个合法文件名的数字片段过长而让扫描失败。

`NaturalSortKey` 因此全程把数字当字符串处理：去掉前导零后，把数字的位数和数字本身编码进可直接字典序比较的 key。这样 `第1卷`、`第2卷`、`第10卷` 会按数值顺序排列，20 位甚至更长的数字也不会溢出。用 `BigInteger` 可以解决溢出，但它仍然是不必要的数值解析；字符串方案更简单，并且保留了任意长度输入的可用性。排序 key 在实体写入时预计算到 `sort_key`，查询时直接 `ORDER BY`，不会在每次目录或条目列表请求中重复解析。

## 10. 与扫描及播放进度的关系

扫描器只负责把磁盘快照对账到 `scanned_file`，视频构建器再通过 `scanned_file_id` 幂等创建 `VideoItem`、`VideoGroup` 和 `VideoFile`。播放端定位文件时重新校验库访问权、物理记录状态、根目录边界和真实路径，路径逃逸、文件消失、资源不存在和无权访问统一使用 404。进度表引用稳定的 `video_file.id`，因此正常改名或移动只改变物理相对路径，不需要迁移播放进度。

- `VideoFolderIndexer` / `VideoBrowseService`：目录树与面包屑
