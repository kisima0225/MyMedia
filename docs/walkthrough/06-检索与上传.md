# 检索与上传 Walkthrough

本阶段给媒体库补上「找得到」和「传得进去」：全文/子串两条搜索路径、标签、播放/阅读
进度旁边的收藏、免登录的分享链接，以及支持断点续传与秒传的分片上传。整个阶段没有
新模块处理"业务逻辑"——搜索和收藏住在各自的领域模块里，标签搭在已经跨两个域的
`metadata` 模块上，只有全局搜索这一个真正跨域的需求换来了一个新模块 `web`。

## 1. 做了什么

### 1.1 两条搜索路径

`video_item` 和 `image_node` 各自多出一个 `search_vector`（`to_tsvector('english', …)`
生成列）和一个 `title`/`name` 上的三元组 GIN 索引（`V12__search_columns.sql`）。
`VideoSearchService`/`ImageSearchService` 在一次查询里同时跑两条路径，取并集：

```sql
WITH scored AS (
    SELECT ...,
           coalesce((title ILIKE :pattern ESCAPE '\' OR original_title ILIKE :pattern ESCAPE '\'), false)
               AS substring_hit,
           greatest(similarity(lower(title), :lowered), ...) AS trgm_score,
           ts_rank(search_vector, plainto_tsquery('english', :raw)) AS fts_score
      FROM video_item
     WHERE library_id IN (:libraryIds)
       AND (title ILIKE :pattern ESCAPE '\' OR ... OR search_vector @@ plainto_tsquery('english', :raw))
)
SELECT ... FROM scored
 ORDER BY substring_hit DESC,
          CASE WHEN substring_hit THEN trgm_score END DESC,
          CASE WHEN NOT substring_hit THEN fts_score END DESC,
          sort_title
```

`GlobalSearchController`（`web` 模块）在这两个域搜索服务之上再包一层，`GET /api/search?q=`
把两边的结果**分区返回**（`{video: [...], image: [...]}`），不做跨域混排——spec §5.4
就是这么要求的，也让排序设计不必解决"视频的 0.6 分和漫画的 0.6 分谁更相关"这种没有
共同尺度的问题。

### 1.2 标签、收藏、分享链接

- **标签**（`tag` / `video_item_tag` / `image_node_tag`，`V13`）：`(domain, slug)` 唯一，
  视频标签与图片标签物理上不能混用。
- **收藏**（`video_favorite` / `image_favorite`，`V14`）：与播放/阅读进度对称，各自是
  `(user_id, target_id)` 复合主键的独立表；图片收藏允许收藏纯目录节点。
- **分享链接**（`share_link`，`V15`）：`library_id` + 两个可空外键
  （`video_item_id` / `image_node_id`）+ `CHECK num_nonnulls(...) = 1`，创建/管理端点
  在两个领域模块（校验访问权需要 `VideoCatalogService`/`ImageCatalogService`），
  令牌解析和 `ShareLinkService` 本身留在 `library`。免登录访问挂在独立前缀
  `/api/share/{token}/**`，`SecurityConfig` 里单独 `permitAll`。

### 1.3 分片上传

`upload_session` / `upload_chunk`（`V16`）记录一次上传的分片账本。流程：

```text
POST /api/upload/sessions              创建会话，服务端算好分片大小；顺带尝试秒传
  └─ 秒传命中 → 会话直接 COMPLETED，不产生第二份物理文件

GET  /api/upload/sessions/{id}         查询已收分片下标列表（断点续传靠这个）

PUT  /api/upload/sessions/{id}/chunks/{index}   逐片写入临时目录
  └─ 片齐 → 条件 UPDATE 转 ASSEMBLING → 排 UPLOAD_ASSEMBLE 任务（dedup_key 兜底）

UPLOAD_ASSEMBLE（后台任务）
  └─ 按序合并 → 校验总大小与内容哈希 → 移入媒体库（重名追加 (2)）→ 触发库扫描
```

## 2. 为什么这样做

### 2.1 分层排序，不是加权求和

`similarity()` 落在 `[0,1]`，`ts_rank()` 通常是 `0.0X` 量级——两个分数根本不在一个
尺度上。把它们乘个权重加起来，只是把"我不知道怎么比"包装成一个看起来精确的数字。
分层排序把这个问题换成了一串优先级判断：先看是不是子串命中（最确定的相关性信号），
命中的一组内部按三元组相似度排，没命中但被全文检索捞到的一组按 `ts_rank` 排，
两层各自的比较都有明确含义，层与层之间不需要换算。

### 2.2 两条路径各管一头，不是重复实现

`ILIKE` 处理中文子串，`tsvector` 处理拉丁文词干化和相关度——`bunny` 能同时命中
`Big Buck Bunny`（子串）和 `The Bunnies Are Running`（`bunny`→`bunnies` 的词干化，
`ILIKE` 做不到）；`movies` 能命中 `Sintel the Movie`（`ILIKE '%movies%'` 是 0 行）。
两条路径不是同一件事的两种写法，删掉任何一条都会丢失真实能力。完整的实测数据、
两字中文查询退化为全表扫描的边界，以及为什么不用 `%` 操作符当匹配谓词，都写在
[ADR-006](../adr/ADR-006-中文搜索的真实边界.md)。

### 2.3 `LIKE` 转义不是可选项

`SearchQuery.of()` 把用户输入过一遍 `escapeLike`：反斜杠先转（否则后转出来的反斜杠
会被再转一次），再转 `%` 和 `_`。不转义的后果不是抛异常，而是**悄悄返回错误结果**——
搜 `50%` 会变成"标题以 50 开头的任意条目"，比崩溃更难发现。这既是一个正确性问题，
也是"用户输入不能直接拼进查询模式"这条更一般纪律的具体例子，`%`/`_`/`ESCAPE '\'`
只是这条纪律在 `LIKE` 上的形状；换成 shell 命令就是参数化调用而不是拼字符串，
换成 SQL 别处就是绑定变量而不是字符串拼接。

### 2.4 域分区的第三次数据库级强制

`video_item_tag`/`image_node_tag` 的复合外键 `(tag_id, domain) REFERENCES tag(id, domain)`，
和 `video_item`/`collection` 用来防止跨域引用的手法完全一样（[ADR-001](../adr/ADR-001-域分区的数据库级强制.md)）：
`tag` 表在 `(id, domain)` 上开一个看似冗余的唯一键，关联表的复合外键就能把 `domain`
钉死——应用层拼错一次 `insert` 语句也无法让视频标签挂到图片节点上，因为数据库会拒绝。

### 2.5 用户态四张表为什么不合并成一个

播放进度、阅读进度、视频收藏、图片收藏是四张独立的表，都不叫"user_data"。
合并成一张表意味着要有一个多态的 `target_type` + `target_id` 列——而 PostgreSQL
建不出跨表的外键引用完整性约束（这正是 2.6 节分享链接要绕开的同一个问题）。
删除一个视频条目时，`ON DELETE CASCADE` 能不能级联到用户数据，取决于目标类型是不是
一个真正的外键；伪装成外键的整数列做不到。四张表各自老老实实地引用自己的目标类型，
每一条级联删除规则都是数据库强制的，不是应用层"记得要删"。

### 2.6 分享链接：两个可空外键 + CHECK，而非多态列

```sql
CREATE TABLE share_link (
    ...
    video_item_id BIGINT REFERENCES video_item (id) ON DELETE CASCADE,
    image_node_id BIGINT REFERENCES image_node (id) ON DELETE CASCADE,
    CONSTRAINT ck_share_link_single_target
        CHECK (num_nonnulls(video_item_id, image_node_id) = 1)
);
```

同样是为了让"目标条目被删了，分享链接要跟着消失"这件事由数据库保证，而不是靠应用层
"记得清理"。代价是每加一个可分享的目标类型就要加一列——本阶段只有两个域，代价可以
接受；域的数量如果长到五六个，会是重新评估这个手法的信号。

### 2.7 令牌即凭证，票据管密码验证的频率

`share_link.token` 是 32 字节 `SecureRandom` 的 Base64URL 编码（43 字符，不是 UUID
那种可预测结构），拿到它本身就是权限——`/api/share/{token}/**` 不要求登录。无效、
过期、已撤销的令牌统一返回 `404`（不是 401/403），不向匿名访客泄露"这个令牌曾经存在
过"这个事实。

带密码的链接如果每次请求都重验 bcrypt，一本漫画翻 20 页就是 20 次 ~100ms 的哈希
运算，阅读体验会直接卡死；但给未登录访客建立服务端会话状态又和"无状态 REST、令牌
即凭证"的设计打架。折中是 `ShareTicket`：解锁一次密码后签发一张自包含的 HMAC 票据
（`<过期时刻的 epoch 秒>.<base64url(HMAC-SHA256(token:过期时刻))>`），服务端不存
任何东西，后续请求带着票据，验证就是重算一遍签名再比对。**票据的过期时刻永远取
"签发时刻 + TTL"和"链接自身的过期时刻"两者中较早的一个**——票据绝不能比它所服务的
链接活得更久，`ShareTicketTest` 里专门有一条用例钉死这一点。签名比较用
`MessageDigest.isEqual`，不用 `String.equals`——后者在第一个不同字节处就返回，
把字符串比较的耗时变成一个可以用统计学方法测出来的旁路信道；前者是恒定时间比较。

### 2.8 `/api/share/**` 与 `/api/shares` 只差一个字母

管理端点（创建、列出、撤销自己创建的分享）在 `/api/shares`（复数，要求登录）；免登录
访问在 `/api/share/{token}/**`（单数）。Spring 的路径匹配按**整段**比较——`/api/share/**`
不会匹配 `/api/shares`，`shares` 这个末尾的 `s` 不会被吃进 `**` 通配符里。这件事光
看代码就能确认，但"我以为路径是这样的"在安全配置上从来不够——`VideoShareControllerTest.theManagementEndpointIsStillBehindLogin`
专门发一个未认证请求到 `/api/shares` 并断言仍是 `401`，把"应该是这样"变成
"跑起来确实是这样"。

### 2.9 分片上传绕开 multipart

Boot 的 `spring.servlet.multipart.*` 默认上限只有 1MB 文件 / 10MB 请求，而且 multipart
解析器会先把内容整个落成临时文件、再交给应用代码读——对于本来就要落盘的分片，这是
白写一遍磁盘。`UploadController.putChunk` 因此走 `application/octet-stream`，直接从
`HttpServletRequest.getInputStream()` 流式写盘，分片内容一个字节都不经过应用内存。
元信息（会话 id、分片下标）全部在 URL 路径里，multipart 能提供的表单字段这里根本用
不上。

`UploadSessionService.receiveChunk` 刻意不是 `@Transactional` 方法：一个 8MB 分片在
慢网络上可能要写好几秒，如果整个方法挂着一个数据库事务，连接池会被一批正在传输中的
请求占满，拖垮应用其它部分。真正的规则是**事务边界贴着数据库操作，不贴着业务动作**：
读会话是一次独立的短事务（`get()`），落盘完全不在任何事务里，记录分片又是一次独立的
短事务（`chunkStore.record()`）。`UploadAssembler.assemble()` 同理——合并一个大文件
要经手几十 GB 的磁盘 I/O，全程没有一个方法带 `@Transactional`，状态变更全部委托给
`UploadSessionService` 的独立短事务方法（`markCompleted`/`markFailed`）。

分片写满后转入合并有两道防线：`markAssemblingIfReceiving` 是一条条件 `UPDATE`
（`WHERE status = 'RECEIVING'`），并发到达的最后两片里只有一个线程能把返回的受影响
行数变成 `1`；即便两边都以为自己赢了竞态，`job` 表的 `dedup_key` 唯一索引是第二道
防线。这与计划 05 给 `cover_asset_id` 做原子回填是同一个手法：判断与写入压成一条
语句，不给"先查后写"的竞态留任何窗口。

### 2.10 秒传的三条边界

`SampledHash`（8 字节大端长度 + 首尾各 1MB 的 SHA-256）本是计划 02 为改名检测设计的，
本阶段复用它做秒传判定和合并后校验。复用带来三条必须说清楚的边界——采样哈希会漏掉
纯中段的差异、秒传只在同一个库内生效、同尺寸候选现算的上限是 8（超过就会"漏"而不是
"错"）。完整的实测依据、为什么不改算法、为什么这个算法形状恰好让浏览器端也能算出
一致指纹，见 [ADR-007](../adr/ADR-007-采样哈希与秒传的边界.md)。

## 3. 坑在哪

### 3.1 `JobPoller.pollOnce()` 是异步提交、同步返回的

`UploadEndToEndTest` 最初按"调一次 `pollOnce()` 就该看到结果"来写断言，全部失败：
`JobScheduler.pollOnce()` 把到期任务提交给线程池就立刻返回，不等处理器跑完。正确
写法是 `await().atMost(...).untilAsserted(() -> { jobPoller.pollOnce(); assertThat(...); })`——
在断言成立之前反复调用，而不是数调用次数。这是计划 03 就踩过、总览交接文档 §2 已经
记录的坑，本阶段在 `UploadEndToEndTest` 上又踩了一次，说明"文档里写过"不等于"这次
会自动想起来"，必须让测试本身在超时内轮询，而不是依赖记忆。

### 3.2 测试类要跑任务，必须显式打开 `JobPoller`

`AbstractIntegrationTest` 默认 `mymedia.jobs.enabled=false`，`JobScheduler` 又是
`@ConditionalOnProperty(havingValue = "true")` 才注册的唯一 `JobPoller` 实现。任何要
`@Autowired JobPoller` 的测试类必须自带
`@TestPropertySource(properties = {"mymedia.jobs.enabled=true", "mymedia.jobs.poll-interval=PT1H"})`——
后一条是为了关掉后台定时轮询，不然它会和测试里手动的 `pollOnce()` 抢任务，产生间歇性
失败。`UploadEndToEndTest` 第一版漏了这一条，报错是 Spring 上下文启动失败
（找不到 `JobPoller` 类型的 bean），不是断言失败，容易被误判成环境问题。

### 3.3 `StreamingResponseBody` 的异步 MockMvc 测试

分享链接的视频流式访问端点复用了 `VideoStreamController` 同款的
`ResponseEntity<StreamingResponseBody>`，响应体由后台线程异步写出。测试如果直接
`mockMvc.perform(get(...)).andExpect(content().bytes(...))`，会在异步写出完成前就
读到空响应体。正确顺序是先 `request().asyncStarted()`，再用 `MvcResult.getAsyncResult()`
取到异步结果，最后 `asyncDispatch(result)` 触发真正的响应派发，`VideoStreamControllerTest`
里已经有这个模式，分享端点的测试照抄即可。

```

```

```powershell
Invoke-WebRequest -Uri http://localhost:8080/api/shares -Method GET
# 期望 401，不是 200 —— 证明路径匹配是整段比较，不是前缀吃掉了整个词
```

### 4.4 跑一遍完整的分片上传

客户端计算采样哈希只需要读文件首尾各 1MB，浏览器端 20 行 JS 就能算出与服务端
一致的指纹（这正是 ADR-007「算法形状让秒传变便宜」这条论据的证明，不是空口白说）：

```javascript
// 采样哈希：8 字节大端长度 ‖ (≤2MB ? 整个文件 : 首 1MB ‖ 尾 1MB)
async function sampledHash(file) {
  const WINDOW = 1024 * 1024;
  const header = new DataView(new ArrayBuffer(8));
  header.setBigUint64(0, BigInt(file.size), false);   // false = 大端

  const parts = [header.buffer];
  if (file.size <= 2 * WINDOW) {
    parts.push(await file.arrayBuffer());
  } else {
    parts.push(await file.slice(0, WINDOW).arrayBuffer());
    parts.push(await file.slice(file.size - WINDOW).arrayBuffer());
  }

  const digest = await crypto.subtle.digest('SHA-256', await new Blob(parts).arrayBuffer());
  return [...new Uint8Array(digest)]
      .map(b => b.toString(16).padStart(2, '0')).join('');
}
```

> 这段 JS 写进文档而不是仓库代码：计划 07 才建前端。它在这里的唯一作用是证明
> 服务端选的指纹算法客户端真的算得出来。

流程：`POST /api/upload/sessions` 拿到 `id` 和分片大小 → 按分片大小切文件，逐片
`PUT /api/upload/sessions/{id}/chunks/{index}`（`Content-Type: application/octet-stream`，
请求体就是那一片的原始字节）→ 片齐后服务端自动排 `UPLOAD_ASSEMBLE` 任务，`GET` 会话
能看到状态从 `RECEIVING` 经 `ASSEMBLING` 到 `COMPLETED`（或因哈希/大小不符落到
`FAILED`）→ 完成后媒体库会收到一次增量扫描，新文件在扫描完成后出现在浏览接口里。

## 5. 交付边界

- 搜索结果不做高亮片段（`ts_headline` 只对 `tsvector` 路径有效，中文走 `ILIKE`，
  两条路径给不出一致的高亮；服务端给一个只有一半情况下存在的字段，比不给更糟）。
- 标签没有重命名与合并端点，建、列、删、贴四件事已够用；重命名牵出 slug 唯一键
  冲突处理，合并牵出关联表去重，两者都属于管理后台范畴。
- `mymedia.share.secret` 默认为空时每次启动随机生成，重启后带密码的链接需要访客
  重新输入密码——已打 WARN 日志；生产部署要配一个固定值,留给计划 08 的 README。
- 秒传只在库内生效，同尺寸候选上限 8 个，超过就会落空走正常上传；落空的代价只是慢
  不是错。
- 上传的临时目录没有过期清理；分享链接的访问没有速率限制（令牌本身 128+ 位熵，
  但带密码链接的 `unlock` 端点理论上可被爆破，bcrypt 本身是一层缓冲）。
- 搜索没有分页，只有 `limit`（上限 200）——媒体库搜索是"找那一部"，不是"翻页浏览"。
