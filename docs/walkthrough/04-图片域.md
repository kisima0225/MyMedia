# 图片域 Walkthrough

本阶段把图片库的物理文件提升为可供浏览和阅读的节点树。与视频域「一部电影、一季是刮削与播放的天然单位」不同，图片的整理方式高度个人化，因此图片域用**任意深度的自由树**建模：目录结构就是用户的整理结果，`image_node` 直接对应目录与压缩包，`image_file` 是挂在节点下的页。物理层的 `scanned_file.id` 仍然是文件的稳定身份，改名与移动不丢任何语义层数据。

## 1. 为什么图片域用自由树、视频域用语义模型

视频的内容结构是**客观的**：一部电影、一季、一集是发行与刮削的天然单位，刮削器能从文件名和 NFO 里可靠地提取它们。因此视频域用 `VideoItem` / `VideoGroup` / `VideoFile` 的语义模型，`VideoFolder` 只是按磁盘目录生成的导航索引——目录不是模型的一部分，改目录名完全不影响条目。

图片的整理结构是**主观的**，真实世界的组织方式深度各不相同：

- 画师 → 年份 → 合集（三层）
- 作者 → 系列 → 单行本 → 卷（四层）
- 来源 → 主题（两层，还可能只有一层）

任何固定层级都会替用户做出错误决定：给「画师/年份/合集」强加卷层是空转，给只有两层的库预留四层是浪费。更根本的问题是**同一棵树里各分支的深度可以不一样**，语义模型无法表达这种自由。因此图片域用任意深度的自由树——树的形状完全由磁盘目录决定，用户怎么整理，树就长什么样。

反过来，视频域不适合树：电影目录下「正片 + 花絮 + 1080p + 4K」的多个文件必须归并成一部作品，树结构只能表达位置、表达不了「这些文件是一回事」，所以视频域的语义层在树之外。

## 2. 「书」与「文件夹」为什么不是互斥类型

一个目录可能**既有散图又有子目录**：既有 `001.jpg`、`002.jpg` 这种直接可读的页，下面又有 `外传/` 这样的子目录。如果「书」和「文件夹」是互斥的类型，这种目录就只能二选一，总有一半内容不可达。

`ImageNode` 因此把它们建模成同一节点的**两种能力**，由两个布尔值表达：

- `isReadable()`：能否进入阅读器。`AUTO` 下看 `directPageCount > 0`。
- `isBrowsable()`：能否进入子项网格。`AUTO` 下看 `childNodeCount > 0`。

两者可以同时为真：既有直属页又有子目录的节点，阅读入口和子项网格入口同时提供，前端渲染为两个卡片或两个操作按钮。阅读模式覆盖（`FORCE_BOOK` / `FORCE_FOLDER`）是用户对这两个布尔值的**显式修正**：`FORCE_BOOK` 让阅读恒真、网格恒假（哪怕页全在子目录里——用户已经声明「这是一本书」）；`FORCE_FOLDER` 正好相反。`AUTO` 是数据说了算，覆盖是用户说了算。

## 3. 两条路径分别管什么

节点同时保存两条路径，各管一件事：

- `materialized_path`：形如 `/1/17/93/`，由**节点 id** 组成，管结构。子树查询是前缀索引扫描，面包屑直接解析出祖先 id 链，都不需要递归。
- `sort_path`：形如 `/1:1:1画师a/1:1:2卷/`，由各级**排序键**组成，管顺序。它存在的唯一理由是 `FORCE_BOOK` 模式要按目录深度优先顺序展开整棵子树的页——id 路径的顺序是创建顺序，与名字顺序无关，所以必须另有一条按名字排序的路径。

改名为什么不动结构路径、却必须重写顺序路径：名字变了，id 一个都没变，`materialized_path` 原样保留；但排序键由名字算出，`sort_path` 里对应的那一段必须跟着重算。`ImageNode.rename` 只重算 `name`、`sortKey` 和本级 `sortPath` 段，`materialized_path` 分毫不动；而 `moveTo` 改父节点时才同时重算两条路径与深度。

## 4. 子树移动为什么必须是一条 UPDATE

改一个节点的 `parent_id` 只移动了它自己——所有后代的 `materialized_path` 前缀还指着旧位置，子树就断了。必须整棵子树一起换前缀，于是 `ImageTreeRelocator.rewriteSubtree` 用**一条 SQL 重写整棵子树**（spec §7.1 明确要求，抄自 `ImageTreeRelocator.java:283`）：

```sql
UPDATE image_node
SET materialized_path = ? || substring(materialized_path FROM ?),
    sort_path         = ? || substring(sort_path FROM ?),
    depth = length(? || substring(materialized_path FROM ?))
            - length(replace(? || substring(materialized_path FROM ?), '/', ''))
            - 1
WHERE library_id = ?
  AND materialized_path LIKE ?
  AND id <> ?
```

参数依次是：新路径前缀、旧前缀长度 + 1、新排序前缀、旧排序前缀长度 + 1（后两个深度表达式再各复用新前缀与旧前缀长度 + 1）、库 id、`旧前缀%`、被移动节点自身 id。

`substring(materialized_path FROM ?)` 里的 `?` 是旧前缀长度加一，即「从旧前缀之后第一个字符开始取」——把每行的旧路径掐掉旧前缀，只留下尾部，再接上 `?` 参数里的新前缀。这里的关键是 **PostgreSQL 的 UPDATE 用行的原始值求值所有表达式**：SET 子句右侧读到的 `materialized_path` 是旧值，写入的是新值，一条语句里既能读旧又能写新，不需要先 SELECT 出来再逐行 UPDATE。

深度用斜杠数算：路径 `/1/17/93/` 里斜杠总数是 4，`length(path) - length(replace(path, '/', ''))` 恰好等于斜杠数，再减 1 就是深度 3。

若改成逐层递归：先查出子节点、逐节点 UPDATE，每个节点都要一次查询加一次写入，一棵 500 节点的子树就是 1000 次数据库往返，而且中途一旦出错，树就处于新旧路径混合的中间态。一条 UPDATE 只有一次往返、由事务原子提交。

## 5. `LIKE '/1/17/%'` 为什么不会误匹配 `/1/170/`

物化路径**以斜杠收尾**：`/1/17/` 而不是 `/1/17`。`LIKE '/1/17/%'` 的语义是「`/1/17/` 后面还能跟任意内容（含空串）」，而 `/1/170/` 在第 5 个字符处是 `0` 不是 `/`，匹配失败。

这个收尾斜杠是物化路径最经典的防线：没有它，`LIKE '/1/17%'` 会把 `/1/170/`、`/1/1700/` 全卷进子树查询和移动操作——子树页数、整目录移动判定、路径重写全都会把不相干的子树算进去，一次改名可能把别人的书一起搬走。这正是 `MaterializedPath.subtreePrefix` 强调必须以斜杠收尾、且 `requireWellFormed` 强制路径以斜杠开头和结尾的原因。

## 6. 页码为什么不在发现文件时分配

文件是扫描时**一个个**来到的。如果发现时就把 `page_index` 按当前计数发下去，中间插入一页会让**后面所有页码全错**：`001, 002, 003` 已经发成 0、1、2，用户在 `002` 前面插入 `002a` 后，它拿到 2，而原来的 2 号（`003`）必须改成 3——逐个修正下去是 O(n²) 次 UPDATE。

正确做法是扫描收尾时**一次重编号**。`ImageLibraryRecalculator.renumberPages` 用窗口函数一条 SQL 搞定：

```sql
UPDATE image_file f
SET page_index = t.rn - 1
FROM (
    SELECT f2.id,
           row_number() OVER (PARTITION BY f2.node_id
                              ORDER BY f2.sort_key, f2.id) AS rn
    FROM image_file f2
    JOIN image_node n ON n.id = f2.node_id
    WHERE n.library_id = ?
) t
WHERE f.id = t.id
  AND f.page_index <> t.rn - 1
```

`row_number()` 在每个节点内按 `sort_key`（自然排序键）排好序号，写回 `page_index`；末尾的 `<> t.rn - 1` 跳过没变化的行——绝大多数扫描什么都不改，不应该产生任何写入。页序的真值是 `sort_key`，页码只是它的产物。

顺带一提，E2E 验证暴露出一个同类问题：`ARCHIVE_INDEX` 任务排在 `LibraryScanCompleted` 之后执行，扫描收尾的重算跑在前面，等索引任务把页填进 `image_file` 时计数已经算完，新索引的压缩包会一直显示 0 页、`readable=false`，直到下次扫描。修复是让 `ArchiveIndexJobHandler` 填页后自己调一次 `libraryRecalculator.recalculate`，复用同一条批量重算管线。

## 7. CBZ 为什么绝不解压到磁盘

ZIP 文件末尾有一块**中央目录区**，记录每个条目的名字、大小和它在文件中的偏移量。因此定位一个条目不需要扫描整个归档，也不存在「必须先解压才能读」的前提——整本解压到磁盘意味着磁盘占用翻倍、临时目录清理逻辑、并发访问冲突三重代价，任何「先解压再读」的实现都不接受。

读取走 `ImageArchiveReader`：

- `listPages` 打开归档，枚举中央目录区条目，过滤出图片扩展名（顺带剔除 `__MACOSX/`、`Thumbs.db` 之类的打包垃圾），按自然排序键排好——归档内条目的物理顺序是打包顺序，不保证有意义。
- `openEntry` 用 `zip.getInputStream(entry)` 按中央目录区的偏移量**直接定位并解压单个条目**，整个过程不落盘；返回的流被包成 `FilterInputStream`，**关闭流时一并关闭 `ZipFile`**——否则文件句柄泄漏，在 Windows 上会导致该压缩包无法被删除或改名。

这层随机访问能力也是页索引存在的理由：不索引的话，每次翻页都得重新打开压缩包、重读一遍中央目录区，一本 500 页的漫画从头读到尾就是 500 次目录区扫描；索引一次写进 `image_file`，之后翻页只按 id 定位条目。

## 8. 压缩包里的中文文件名为什么会乱码

ZIP 规范对条目名编码有个通用位标记：**第 11 位**（`usesUTF8ForNames`）。打了这个标记，条目名就是 UTF-8；没打，编码由打包工具决定——Windows 中文工具（好压、WinRAR 中文版等）的典型产物是 GBK。两个时代的归档混在一起是常态，只用一种编码打开必然乱码。

Commons Compress 的做法是**逐条目检查第 11 位**：打了标记的按 UTF-8 解，没打的才用构造时传入的**回退编码**。JDK 自带的 `ZipFile` 做不到：它要求整个归档用同一种编码，遇到解不开的字节直接抛异常。

回退编码设成 `GBK` 是安全的，因为它只作用于**没打标记**的归档。实测（`jar` 生成的 UTF-8 归档，分别用 UTF-8 与 GBK 打开）：

| 条目 | UTF-8 打开 | GBK 打开 | 通用位标记 |
|---|---|---|---|
| `第1章/001.jpg` | `e7acac31e7aba02f...` | `e7acac31e7aba02f...` | `usesUTF8ForNames = true` |

两种配置得到**完全相同的字节**：打了标记的条目，commons-compress 直接按 UTF-8 解，配置的 charset 根本不参与。这就是 `mymedia.image.archive-charset` 配置项存在的全部理由。

## 9. 目录改名时用户数据是怎么保住的

分两层看。

**物理层**：扫描器发现一批「旧路径消失、新路径出现」的文件，`RelocationDetector` 用**采样哈希**配对它们——`SampledHash` 对超过 2MB 的文件只取头尾各 1MB 窗口和文件长度算摘要，避免整文件哈希拖慢扫描。配对的双方共享同一个 `scanned_file.id`，物理身份不变。

**语义层**：`ImageTreeRelocator` 收到移动事件后按（旧目录 → 新目录）分组。关键判据是**整组搬完才算目录移动**：把「组内文件数」与「旧目录节点的整棵子树文件数」对比——相等说明整个目录搬走了，于是改名/移动节点本身（子树上的进度、阅读模式、页全部跟随）；不等说明只是零散文件搬家，逐文件重挂即可。判据按 `DISTINCT scanned_file_id` 数而非页数：一个压缩包是一个文件、N 页，按页数比会把只含压缩包的目录误判成「没搬完」。判定从基目录逐层上溯，祖先的整棵子树都搬走时它也一起搬，父子同时改名的多段场景由全链候选逐一落实；整棵子树用第 4 节那条 SQL 一次重写。

**空壳节点从哪来、怎么回收**：扫描时先按新路径 find-or-create 节点、再做改名配对，前者已经建好的节点若配对后被判定为「已由旧节点顶替」，就空在那里——零页零子节点的残留目录。两处清理：移动前 `clearGhostAt` 检查目标位置，若被空壳占据且无真实内容则删掉再搬，否则整目录移动放弃、回落逐文件重挂；扫描收尾的重算里 `pruneEmptyDirectories` 循环删除零页零子节点的 `DIRECTORY` 节点（**只回收 DIRECTORY**——还没跑索引任务的 `ARCHIVE` 节点页数也是 0，把它当空壳删掉等于把整本书弄丢）。

阅读进度引用稳定的节点 id，节点跟着目录走，进度自然跟随。E2E 最终验收正是这条链路：给 `画师A/2024` 下某节点记录进度，把 `画师A` 改名为 `画师A（已整理）` 再扫描，`continue-reading` 仍返回同一个节点、同一页进度，顶层树里没有残留的旧目录或空壳。

相关实现：

- `ImageNode` / `ImageNodeIndexer`：节点模型（双路径、双布尔能力）与 find-or-create 索引器
- `ImageTreeRelocator`：目录改名/移动的分组判定与子树单条 UPDATE 重写
- `ImageLibraryRecalculator`：扫描收尾的批量重算（重编号、重计数、空壳回收）
- `ImageArchiveReader` / `ArchiveIndexJobHandler`：CBZ 随机访问与页索引
- `ImageContentBuilder` / `ImageScanFinalizer`：扫描事件到节点树的翻译与收尾
