# ADR-008：媒体票据

## 状态

已接受（2026-08-17，实施计划 07）

## 背景

ADR-002 选了 HTTP Basic + 无状态会话作为认证方案。这个决定在计划 01–06 的纯 API 场景下
没有任何问题——每一次请求都带 `Authorization: Basic ...` 头，服务端逐次校验，不留会话状态。

计划 07 第一次让浏览器直接渲染媒体内容：`<video src="...">`、`<img src="...">`。这两个标签
由浏览器自己发起 GET 请求，**没有任何办法附带自定义请求头**——不是 Basic 的缺陷，而是所有
「凭证放在请求头里」的方案共同的约束：换成 Bearer JWT 一样带不了，换成任何自定义 header
方案都一样带不了。这条约束逼着这三条只读媒体路径必须换一种凭证携带方式：

- `GET /api/video/stream/{fileId}`（视频流，Range 播放）
- `GET /api/image/page/{fileId}`（图片单页）
- `GET /api/assets/{id}`（封面/缩略图/雪碧图等派生资源）

## 决策

新增一条短期、自包含的 HMAC 票据机制：登录用户调用 `POST /api/auth/media-ticket` 换取一张
`<userId>.<过期时刻 epoch 秒>.<base64url(HMAC-SHA256)>` 形状的票据，前端把它作为
**query 参数**（`?ticket=...`）拼在上述三条路径的 URL 上。一个装在 `BasicAuthenticationFilter`
之前的过滤器（`MediaTicketAuthenticationFilter`）在这三条路径上校验票据、把它换成标准的
`SecurityContext`，下游 27 个既有控制器一行不改——`@AuthenticationPrincipal`、
`LibraryAccessService.canAccess`、「404 而非 403」的规矩全部照常生效，它们根本不知道
票据这条通道存在。

签名原语提取到新类 `shared.HmacSigner`（`ShareTicket` 同步重构为委托它，外部行为一个字节
不变），票据 TTL 15 分钟，前端在过期前 30 秒自动续签。

## 理由

- **保住 ADR-002 的两个核心承诺**：服务端仍然不存储任何会话状态，票据校验就是重算一遍签名
  再比对；`csrf().disable()` 的理由依然成立——票据和 Basic 一样不是 Cookie，不会被跨站请求
  自动携带。
- **复用已验证过的机制**：`library.ShareTicket`（分享链接解锁后的通行证）已经在生产路径上跑
  过同一套 HMAC 签名与校验逻辑。把签名算法提到 `shared.HmacSigner` 让两者共用同一段代码，
  与 G8 把 `SampledHash` 从 `scan` 提升到 `shared` 是同一个先例——**第二个消费者出现时才
  提取，不提前抽象**。`user` 模块因此仍然只依赖 `shared`，不需要碰任何 `allowedDependencies`。
- **密钥留空时随机生成是这里的正确默认**：15 分钟 TTL 加前端自动续签意味着重启后最坏结果
  只是前端多取一次票据；这与 `ShareTicket`（密钥留空会让带密码的分享链接在重启后要求访客
  重新输入密码，是 G14 记录的用户可感知缺陷）刚好相反——同一个签名算法，两种生命周期，
  两种默认值，理由各自独立成立。

## 后果

凭证以 query 参数形式出现在 URL 里，会漏进服务器访问日志、跨站请求的 `Referer` 头、浏览器
历史记录。**路径白名单是对这个后果的直接缓解，不是回避**：票据只在这三条只读路径上被接受，
拿它能干的事被钉死在「看一段视频、看一页图、看一张封面」——泄漏的代价上界是「有人多看了
几部片子」，不是「有人删了媒体库、改了用户资料」。15 分钟的短 TTL 进一步压缩了一次泄漏的
有效窗口。

## 备选方案

| 方案 | 为什么没选 |
|---|---|
| Cookie 会话 | `<video>`/`<img>` 能直接工作，但要推翻 ADR-002：重新引入 CSRF 攻击面与服务端会话状态，代价是架构性的，不是局部的 |
| fetch 整个文件再转 blob URL | 图片勉强可行（文件通常几百 KB 到几 MB），视频不可行——一部电影要整个读进内存才能拿到 blob URL，而且完全丢掉 HTTP Range 与浏览器原生的拖动定位，把计划 03 里技术含量最高的那条播放链路直接作废 |
| Service Worker 拦截请求注入头 | 理论上能同时保住无状态与「凭证不出现在 URL 里」，但 Service Worker 的生命周期、多标签页间的注册时序、以及它本身只在部分浏览器/隐私模式下可靠这几件事叠在一起，会让一个自托管单实例项目背上一套只在调试时才会现形的中间层复杂度，不划算 |

## 未做

**带密码的分享链接不支持媒体流播放**（详见 Task 16 的实现说明）：分享票据走的是
`X-Share-Ticket` **请求头**（不是 query 参数），而 `<video src>`/`<img src>` 同样带不了
自定义头。给分享票据也开一条 query 参数入口，形式上和媒体票据一样，但后果完全不同——
分享链接的 URL 本来就是**设计给到处转发**的东西，转发一次就等于把密码保护整个废掉。
这是刻意的取舍，不是遗漏。若将来要做，正确的形态是让 `VideoShareController`/
`ImageShareController` 也接受 `?ticket=` 且把这张票据的 TTL 压到分钟级，把「转发链接=永久
生效」的窗口收窄到「转发链接=几分钟内生效」，留给计划 08 之后按需评估。
