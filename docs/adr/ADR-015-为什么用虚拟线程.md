# ADR-015：为什么用虚拟线程

## 状态

已接受（2026-08-17，实施计划 08）

## 背景

MyMedia 的核心工作负载几乎全是阻塞 I/O：大文件的 Range 流式传输、ZIP
归档随机读单页、外部进程调用（ffmpeg/ffprobe）、刮削链对外部提供者的
HTTP 请求。传统方案要么用平台线程池（受限于线程数，需要在吞吐与内存
之间反复调参），要么用响应式编程模型把整条调用链改成回调/操作符风格。
JDK 25（本项目的 `java.version`，`pom.xml:17`）是虚拟线程转正后的第一个
LTS 版本，这类阻塞 I/O 场景正是它的设计目标。

## 决策

`spring.threads.virtual.enabled: true`（`src/main/resources/
application.yml:5-6`，注释写明「本项目是重阻塞 I/O 场景」）开启 Spring
的全局虚拟线程支持；此外任务调度器与外部进程读取两处显式用虚拟线程
工厂，不依赖框架默认值：

1. **`JobScheduler.java:37`**：`Thread.ofVirtual().name("mymedia-job-",
   0).factory()` 建任务执行器（`Executors.newThreadPerTaskExecutor(...)`），
   每个被抢占的任务在独立虚拟线程里执行。
2. **`JobScheduler.java:39`**：租约续期的 `heartbeatExecutor` 同样用
   `Thread.ofVirtual().name("mymedia-lease-", 0).factory()` 建线程池
   （`Executors.newScheduledThreadPool(1, ...)`）。
3. **`ProcessCommandRunner.java:64`**：`Thread.ofVirtual().start(...)`
   分别起线程读子进程的 stdout 与 stderr（`drain()` 方法，
   `ProcessCommandRunner.java:63-71`）。**这一处不是为了性能，是为了
   正确性**：类上的 Javadoc（`ProcessCommandRunner.java:14-24`）写得
   很直接——ffmpeg 往 stderr 写进度，管道缓冲区满了就会阻塞，表现为
   「卡死」；不并发读走两个流，单线程顺序 `waitFor()` 会直接死锁。

## 理由

本项目是彻头彻尾的阻塞 I/O 场景：大文件 Range 流式传输、ZIP 随机读
单页、外部进程调用、刮削 HTTP 请求，没有一处是 CPU 密集型的计算负载。
虚拟线程正好对这个形状——一个请求一个线程的写法保住了（栈追踪可读，
出错时能看到完整的调用链，调试和响应式风格比起来简单得多），而阻塞
调用不再占着平台线程：虚拟线程在阻塞时会自动释放底层的载体线程
（carrier thread）去执行别的虚拟线程，等 I/O 就绪再恢复。这意味着
不需要为「同时处理多少个长连接的视频流」这类问题去调 Tomcat 线程池
大小——线程本身足够便宜，可以按请求数创建而不是复用一个有限的池子。

## 坑

写这一条是因为踩过或者刻意确认过，不是抄文档：

- **`synchronized` 块里阻塞会 pin 住载体线程**：虚拟线程在
  `synchronized` 临界区内执行阻塞操作时，无法被卸载，会占住底层
  平台线程直到临界区结束。JDK 24 起的 JEP 491（Synchronize Virtual
  Threads without Pinning）大幅缓解了这个问题，但 `synchronized` +
  阻塞 I/O 的组合仍然值得主动避开，而不是依赖运行时版本兜底。
- **把连接池/对象池挂在 `ThreadLocal` 上的老套路在虚拟线程下失效**：
  这套模式假设「线程数量有限、生命周期长，可以在线程上缓存昂贵对象」，
  而虚拟线程恰恰是海量且短命的——每个请求一个新线程，`ThreadLocal`
  缓存的收益消失，反而增加内存占用。
- **线程转储要用 `jcmd <pid> Thread.dump_to_file -format=json
  <file>`**，老的 `jstack` 看不到虚拟线程——排查「卡住了」这类问题时，
  用惯 `jstack` 的人会得到一份看起来正常、实际上遗漏了绝大多数活跃
  线程的转储。

## 后果

不需要调 Tomcat 线程池大小去匹配并发请求数——这是虚拟线程最直接的
收益，也是本项目选它的主要动机。但**数据库连接池反而成了新的瓶颈
点**：虚拟线程可以创建到数以万计，数据库连接不行。本项目没有显式
配置 HikariCP 连接池大小（`application.yml` 里没有
`spring.datasource.hikari.*` 相关键），走的是 Spring Boot 的默认上限
（10）。这一条要老实写：虚拟线程解决了「线程数量」这个瓶颈，但没有
让「数据库连接数」这个瓶颈消失，如果代码里出现「用虚拟线程并发发起
大量数据库查询」的写法，真正卡住吞吐的会是连接池而不是线程调度——
这是虚拟线程最常见的误用场景，不写清楚等于没吸取教训。

## 备选方案

- **平台线程池**（调 `server.tomcat.threads.max` 之类的参数）：需要
  在吞吐与内存之间反复试探合适的池大小，且池大小本身要随负载特征
  变化（长连接的视频流 vs. 短平快的 API 调用需要的池大小完全不同）。
  虚拟线程把这个调参问题直接消掉了。
- **响应式编程（WebFlux）**：吞吐上限更高，但要把整个代码库改写成
  回调/操作符风格——`Mono`/`Flux` 链替代直接的方法调用，栈追踪在
  异常发生时不再对应到业务逻辑的调用路径，调试成本显著上升。换来的
  收益是「同一个阻塞 I/O 场景」虚拟线程已经用远低得多的心智成本解决
  了的问题。对一个要求「每一处技术选型都能讲清楚为什么」的项目，
  WebFlux 是负分：它解决的问题本项目不存在（没有那么高的并发量级），
  代价（代码风格全面改写）却是实打实的。
