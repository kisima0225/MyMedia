# ADR-011：物理层与语义层分离

## 状态

已接受（2026-08-17，实施计划 08）

## 背景

扫描发现的是磁盘上的文件，用户看到的是「一部电影」「一本漫画」。这两者
不是一回事：同一个物理文件在被解析出语义之前只是路径、大小、修改时间；
而语义条目（标题、集数、播放进度、收藏、标签）一旦建立，用户会持续在
它上面积累状态。如果这两层没有分开建模，「整理媒体库」这个最常见的
用户操作——改名、移动、重新归类——就会把语义状态一起带丢。

## 决策

`scanned_file`（`V5__scanned_file.sql`）是纯物理层：只记录
`relative_path` / `size_bytes` / `mtime` / `content_hash`（采样哈希）/
`status`（`ACTIVE` / `MISSING`），不含任何领域语义。`video_item` /
`video_file` 与 `image_node` 是语义层，通过外键引用 `scanned_file`。
两层之间只有外键连接，语义层不反向决定物理层的存续，物理层也不知道
自己被解释成了什么。

## 理由

如果只有一层——路径既是物理位置又是语义条目的标识——那么「改名」在
数据模型里等价于「删除旧条目 + 新建条目」，用户的播放进度、阅读进度、
收藏、标签全部挂在旧条目的外键上，随之全部丢失。

分成两层之后，改名检测（`RelocationDetector`，采样哈希算法见 ADR-007）
只需要认出「这仍是同一个物理文件」，把 `scanned_file` 的 `relative_path`
原地更新，`scanned_file.id` 保持不变——外键指向它的一切语义状态、进度、
收藏都还在，不需要任何补偿逻辑。

## 实证

- `RelocationDetector.detectAndApply`：按当前扫描新增/消失的两个 id 集合，
  用采样哈希配对「消失的文件」与「新增的文件」，判定为改名而非
  删除+新建，写入 `ScannedFileRelocated` 事件。
- `ImageTreeRelocator.tryMoveWholeDirectory`：目录整体改名/移动时，
  用一条前缀替换 `UPDATE` 把整棵子树的路径一次性搬走，而不是逐文件
  删除重建。这条路径上出过两次真实缺陷（总览与交接 §9）：**P2**——
  只搬到组的最底层节点，顶层目录整体改名时旧祖先被误判为空壳回收；
  **P7**——合并前 review 发现目录被**上移**（新路径比旧路径更浅）时
  下标越界，异常从 `ImageScanFinalizer` 冒出去导致扫描任务本身失败、
  队列永不排空。两次都已修复（提交 `19d5a6c` 修了 P7），并补了回归
  测试（`movingANestedDirectoryUpToTheRootKeepsItsNode` 等）。这两次
  修复恰恰说明「物理层内容不变、路径变化时语义要原地跟随」这条设计
  在实现上并不是免费的——路径重写本身有真实的边界情况要处理。
- 进度表（视频播放进度、图片阅读进度）挂的是 `scanned_file` 派生出的
  语义条目 id，从不挂路径字符串——这是两层分离在下游表结构上的直接
  体现。

## 后果

两层需要对账：`ScanReconciler` 把一次目录遍历的结果与 `scanned_file`
现有记录比对，产出新增/更新/消失三类结果。对账会产生孤儿——语义层
条目关联的物理文件全部消失或被重新配对走了，此时需要收尾器清理：
`VideoScanFinalizer` 与 `ImageScanFinalizer` 在 `LibraryScanCompleted`
事件后各自清理「没有任何物理文件」的语义条目。二者都明确只清理真正
的孤儿——`scanned_file` 只是被标记 `MISSING`（文件仍能在后续扫描中被
重新发现并 `reactivated`）不会触发清理，只有语义条目彻底没有物理文件
关联时才回收。

**扫描绝不删除物理层数据**——文件在磁盘上消失时，`scanned_file.status`
只置为 `MISSING`，这一行本身不删除。所有「回收」逻辑都建立在这个前提
之上：物理层的删除是显式的、只在语义层确认孤儿之后才发生，而不是扫描
遍历的副作用。

## 备选方案

- **单层模型**（路径即主键，语义字段直接挂在扫描表上）：改名即等价于
  删除+新建，进度/收藏/标签全部丢失，是本 ADR 明确要避免的问题本身。
- **用绝对路径当主键**：移动到库外或跨库移动直接丢失身份；且
  Windows/Linux 路径大小写与分隔符规则不一致，拿路径字符串做身份标识
  比拿自增 id 更脆弱。
- **每次扫描全量重新哈希所有文件来确认身份**：正确，但慢——ADR-007
  已经算过这笔账：全量哈希需要读完整个文件，采样哈希（首尾若干 KB +
  大小 + mtime）用可接受的误判率换来了数量级的速度提升，全量哈希对
  大型媒体库的扫描时长不可接受。
