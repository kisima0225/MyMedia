# ADR-009：为什么是模块化单体

## 状态

已接受（2026-08-17，实施计划 08）

## 背景

MyMedia 是单实例自托管的媒体库服务，交付形态是「本地 `docker compose up`」，
没有公网部署、没有多租户、没有跨团队协作——开发者只有一个人。设计文档
§2 的非目标表把「微服务」明确列了进去，理由写得很直接：**「严重过度设计。
『为什么拆』这个问题现阶段答不了。」** 微服务的核心收益是独立部署、独立
扩缩容、团队边界与技术栈解耦，这四条在单实例自托管场景下没有一条成立。

但普通的分层单体（`controller` / `service` / `repository` 三层，模块之间
随意 `import`）也有真实问题：随着视频域、图片域、扫描、刮削、预览各自
长成一摊代码，「谁能依赖谁」这件事只存在于开发者脑子里和代码评审的记忆
里，没有任何东西会在它被违反时报错。

## 决策

顶层 Java 包即 Spring Modulith 的应用模块：每个模块的 `package-info.java`
上标注 `@ApplicationModule`，并显式声明 `allowedDependencies`——只写
`displayName` 不写 `allowedDependencies` 等于对该模块不设限，这是一个真实
出现过的坑（见下文实证）。测试阶段跑 `ApplicationModules.verify()`
（`src/test/java/com/mymedia/ModularityTests.java`），任何一次跨模块的
非法依赖都会让这个测试直接失败。

## 理由

普通分层单体本身不是错的，它错在**没有强制点**——模块边界靠开发者自觉，
而自觉这种东西撑不过三个月：某次为了赶一个功能，「就这一次」从 `video`
里直接 `import` 了 `scan` 的内部实现类，下一次评审没抓到，边界就永久地
破了一个口子，且不会有任何信号提示这件事发生过。

模块化单体把这条边界从「大家记得」变成了「测试期会失败的断言」，代价
只是一个注解加一条 `allowedDependencies` 声明。这不是理论推演——2026-08-19
做过一次真实验证（记录在总览与交接 §3）：把 `video` 模块的
`allowedDependencies` 临时收紧成 `{"shared"}`（即禁止它依赖 `library` /
`scan`），立刻重跑 `ModularityTests`，测试**立刻报出 11 条越界依赖**，
分布在 `library`、`scan`、`scan :: spi`、`scan :: events` 四个方向；改回
实际需要的依赖集合后测试转绿（`ModularityTests` 2 tests 0 failures）。
**这条 RED/GREEN 实证是「这套机制真的会拦人」的唯一证据**——没有它，
`allowedDependencies` 就只是一段没人验证过是否生效的样板注解。

## 后果

跨模块访问只能走两种通道：模块的公开 API（`public` 类），或显式标了
`@NamedInterface` 的命名接口（如 `scan.spi` 包对外暴露为 `scan::spi`，
`scan.event` 包对外暴露为 `scan::events`）。实现类与 Repository 默认
package-private，天然不可跨模块引用。`scan` 想要保持「不依赖任何领域
模块」，代价是做了一次 SPI 倒置——定义 `LibraryContentBuilder` 接口
（`src/main/java/com/mymedia/scan/spi/LibraryContentBuilder.java`，三个
回调 `onFileDiscovered` / `onFileChanged` / `onFileVanished`），由 `video`
与 `image` 反向实现并注入，而不是 `scan` 主动 `import` 领域包。

命名接口的名字必须逐字写对：`allowedDependencies` 里的字符串如果拼错
（比如把 `scan::events` 写成 `scan::event`），不会得到一条断言失败，而是
`ApplicationModules` 在**加载期**直接抛异常——一旦发生，整批架构测试
一起挂掉，不会区分「哪条依赖写错了」，只能逐个 `package-info.java` 排查。

## 备选方案

- **微服务**：如上，收益（独立部署/扩缩容/团队解耦）在单实例自托管场景
  下无一成立，是纯粹的过度设计，且「为什么要拆」这个问题现阶段答不上来。
- **普通分层单体**：零额外成本，但没有强制点——边界的存续完全依赖开发
  者记忆与代码评审的覆盖率，三个月后大概率被侵蚀。
- **六边形架构 / 整洁架构的完整仪式**：每个模块套 `domain` / `application`
  / `infrastructure` 三层加端口适配器，对当前规模（11 个模块、单人开发）
  是仪式感大于收益的负担，且不解决「跨模块依赖」这个真正的问题——
  六边形架构约束的是模块内部分层，不是模块之间的边界。
