# ADR-012：两个域的不对称组织模型

## 状态

已接受（2026-08-17，实施计划 08）

## 背景

MyMedia 同时管理视频与图片（漫画/图集）两类媒体。一个自然的冲动是给
两者套同一套「媒体条目」抽象——毕竟都是「文件在文件系统里，需要被
浏览、搜索、收藏」。但视频与图片在「什么是一个条目」这件事上，真实结构
完全不同：视频有 `S01E01` 这类广泛遵守的命名约定，漫画与图集则可能是
一个 CBZ、一个装满散图的目录、或者一个包着若干章节子目录的目录——
没有等价的约定。

## 决策

视频域是**语义树**：`video_item` / `video_group`（`V6__video_domain.sql`
的 `video_group` 表，`item_id` + `group_index` 组织一部剧的季/篇章）/
`collection`（`collection` + `collection_item` 关联表），从文件名解析出
`S01E01` 这类结构化信息。图片域是**自由树**：`image_node` 用物化路径
（`V8__image_domain.sql`）表示任意深度的目录层级，目录结构本身就是用户
的整理结果，不做命名解析；外加 `reading_mode` 列（`AUTO` / `FORCE_BOOK`
/ `FORCE_FOLDER`，`ck_image_node_reading_mode` 约束）让用户在自动判定
不准时手动覆盖「这个节点该当书还是当文件夹浏览」。两个域的模型不共享，
只共享 `shared` 里的两个纯算法类：`NaturalSortKey`（自然排序）与
`MaterializedPath`（物化路径运算）。

## 理由

视频的命名约定（`S01E01`、季号、集号）是行业级的、广泛遵守的，解析它
有真实收益——用户不需要手动整理，系统就能正确分季分集。漫画与图集
没有等价物：「一本书」在磁盘上可能是一个压缩包、一个目录、或嵌套目录，
不存在一套能覆盖大多数场景的命名规则。如果强行给图片域也套一层语义
解析，`reading_mode` 这种覆盖开关会从「少数场景的例外」变成「大多数
场景都要手动纠正」的常态——这就是没有选择这条路的原因。

## 这条判断一路贯穿到前端

同一条「视频有统一形状、图片没有」的判断，在数据层和表现层各表达了
一次：视频域用等高的 16:9 网格（`VideoCard.vue:66` 的
`aspect-ratio: 16 / 9`）——视频封面天然接近 16:9，裁切统一比例不会
丢失关键信息；图片域用 CSS 多列瀑布流（`NodeGrid.vue:37/43`，
`columns: 5 200px` 配合 `break-inside: avoid`，响应式断点在窄屏降到
`columns: 3 140px` / `columns: 2 130px`）——漫画封面的比例天差地别，
强行裁成统一比例会把标题文字或角色脸切掉。**同一条判断在数据层和
表现层各表达了一次**，这是这篇 ADR 最值钱的部分：不是「两处恰好都不
一样」，而是「不一样」本身就是同一个根因（视频有统一形状、图片没有）
在两个层次上的必然结果。

## 后果

两个域的服务、控制器、DTO 大面积逐字对称重复：搜索
（`VideoSearchService` / `ImageSearchService`）、收藏、分享各有一套
几乎平行的实现。计划 06 的最终审查把这条明确记为**刻意取舍**而不是
坏味道：抽一个公共模块出来，代价是要引入「目标类型」多态列去区分
「这条收藏/分享指向的是视频还是图片」，而本项目一直在避免那个方向——
`share_link` 表（`V15__share_link.sql`）就是同一条判断在另一处的体现：
它用「两个可空外键（`video_item_id` / `image_node_id`）+ `CHECK` 恰有
一个非空」而不是 `(target_type, target_id)` 多态外键来表达「分享指向
两者之一」，理由写在迁移脚本的注释里——**多态外键在 PostgreSQL 里建不了
引用完整性约束**，任何指向已删除资源的脏数据都不会被数据库拦下来。
不共享模型换来的是：每个域的每一列都有实打实的外键约束，代价是重复。

## 备选方案

- **统一「媒体条目」模型 + `type` 字段**：`type = VIDEO` 的行不需要
  `reading_mode`，`type = IMAGE` 的行不需要 `group_index`——会长出一堆
  彼此互斥的 nullable 列，和大量按 `type` 分支的 if/else，可读性与
  数据完整性都比现在差。
- **给图片域也套语义解析**（尝试从目录/文件名猜测「卷」「话」结构）：
  漫画与图集的命名没有视频那种广泛共识，猜测经常出错，`reading_mode`
  这个本该是例外的覆盖开关会变成用户几乎每次整理后都要手动纠正的
  常态操作，体验比不做解析更差。
